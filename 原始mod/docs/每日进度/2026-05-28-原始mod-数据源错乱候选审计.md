# 原始mod 数据源错乱候选审计

- 范围：`游戏数据/官方合作指挥官/commanders/*/{units,buildings,heroes}.json`
- 目的：定位为什么 `CommanderTestBench` 当前导出的兵种/建筑面板清单会出现明显错乱。
- 口径：这份审计只标记“高风险候选”，不直接当作最终裁决。它用于指导后续修改 `scripts/sc2/generate-xmfinal-commander-profiles.mjs` 的过滤、映射和白名单规则。

## 结论摘要

- 当前错乱的主因不在测试台，而在数据源到 Galaxy roster 的生成口径过粗。
- 现有生成脚本对 `units.json` / `heroes.json` / `buildings.json` 基本按 `unit_id` 直接收集，缺少“这是不是当前指挥官真实面板项”的二次筛选。
- 高风险对象主要集中在 5 类：
  - 共享对象：同一个 `unit_id` 同时属于多个指挥官，命令卡和按钮天然容易串线。
  - 形态体/变体：如飞行态、攻城态、埋地态、升阶态、展开/收起态，不一定应该作为独立面板项。
  - 工蜂/经济单位：是否应该进入“兵种面板”取决于口径，当前脚本没有区分“全部单位”和“作战面板单位”。
  - 生产入口不明确：`production.producer_unit_id` 或 `button_face` 缺失，通常意味着该对象更像英雄态、召唤物、形态体或共享数据残留。
  - 英雄对象：很多英雄条目并不适合直接和普通兵种混排，需要单独规则。

## 原因标签说明

| 标签 | 中文含义 | 说明 |
| --- | --- | --- |
| `共享对象` | 同一对象被多个指挥官复用 | 极易把别家按钮、技能、需求条件带进来 |
| `形态体/变体` | 同一兵种的另一形态或派生形态 | 不一定应该单列为独立面板项 |
| `工蜂/经济单位` | 工作者、采集者、建造者 | 是否保留要看测试台口径 |
| `生产入口不明确` | 缺少稳定的生产者或按钮入口 | 更像共享残留、特殊态或待单独处理对象 |
| `英雄对象` | 英雄本体或英雄相关对象 | 应优先单独归类，不宜直接混到普通兵种清单 |

## 后续修正建议

1. 不要继续把 `units.json` / `heroes.json` / `buildings.json` 里的全部 `unit_id` 直接写进 XMFinal roster。
2. 在 `generate-xmfinal-commander-profiles.mjs` 里增加“面板项白名单/黑名单”层，而不是只做 alias。
3. 对以下对象优先加过滤规则：
   - 共享基础单位：`Zergling`、`SwarmQueen`、`Observer`、`SCV`、`SiegeTank`、`ImmortalAiur`
   - 形态体：`*Burrowed`、`*Sieged`、`*Flying`、`*Assault`、`*Uprooted`
   - 工蜂/经济单位：`*Drone*`、`SCV*`、`*Probe*`
4. 英雄对象单独处理，不要默认与普通兵种共用同一 roster 口径。
5. 修完后必须重跑：
   - `node .\scripts\sc2\generate-xmfinal-commander-profiles.mjs --write`
   - `pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\sc2\export-originalmod-testbench-rosters.ps1`
   - 再对照 `CommanderTestBench` 本地清单复核。
