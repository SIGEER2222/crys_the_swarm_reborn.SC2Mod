# 7vs1 外部 Mod 指挥官信息整理

## 结论先行

这批外部数据的指挥官逻辑不是“每个指挥官都用私有基地和私有工人”。

它更接近官方合作指挥官的运行方式：先把玩家设置成某个 `PlayerCommanders` 实例，再按 `SpawnRace` 读取 Race Catalog 的开局单位，然后通过 `DefaultUpgrades`、`DefaultAbilityCommands`、英雄/全局施法单位、UI 分发和 `LibKMIS` 触发完成 commander 专属闭包。

因此，凯瑞甘、扎加拉、阿巴瑟在这批外部数据里 `SpawnRace` 都是普通 `Zerg`。它们的开局基地/工蜂不是私有 ID，而是普通虫族 Race 继承出来的开局主城和 `Drone`；专属性来自 `KerriganCommander`、`ZagaraCommander`、`AbathurCommander` 等默认升级和对应能力/需求链。如果我们当前 Mod 要求“每个指挥官单位都独立”，不能照搬这个外部 Mod 的 `SpawnRace=Zerg` 做法，必须给这些指挥官建立私有开局主城、工人、幼虫/变异能力和完整科技限制闭包。

### set_commander_for_player 做了什么

`libKPVP_gf_set_commander_for_player` 的关键动作：

| 步骤 | 逻辑 | 影响 |
| --- | --- | --- |
| 记录玩家 commander | `libKCOR_gf_CC_PlayerCommanderSet(player, commander)` | 写入 `ActiveCommanderForPlayer` |
| 设置出生种族 | `PlayerSetRace(player, libKCOR_gf_CC_CommanderSpawnRace(commander))` | 后续开局主城/工人按 `SpawnRace` 取 |
| 设置满级 | 固定 `lv_currentLevel = 15` | 当前外部 Mod 默认按满级处理 |
| 设置威望 | 读取玩家属性，设置威望索引 1/2/3 | 后续 `ApplyPrestigeTech` 生效 |
| 设置精通 | 三组选项映射到 0/30、5/25、...、60/60 | 写入对应 commander 的 `MasteryUpgrades` |
| 应用科技 | `libKCOR_gf_CC_ApplyTech(player)` | 应用军队、指挥官、等级、种族、威望、精通科技 |
| 额外解锁 | `libKPVP_gf_enable_upgrades_for_player` | 例如诺娃、雷诺、霍纳、蒙斯克的额外升级允许 |

### 开局主城和工人怎么来

`LibKPVP.galaxy` 的开局函数通过下面这条链取主城：

```text
ActiveCommanderForPlayer(player)
-> PlayerCommanders[commander].SpawnRace
-> RaceCatalog[SpawnRace].StartingUnitArray[0].Unit
```

代码证据是 `lv_townHallType = CatalogFieldValueGet(c_gameCatalogRace, libKCOR_gf_CC_CommanderSpawnRace(...), "StartingUnitArray[0].Unit", c_playerAny)`。

这意味着：

| SpawnRace | 当前可见开局 | 来源 | 是否私有 |
| --- | --- | --- | --- |
| `Prot` | 主城继承普通星灵开局，工人 `Probe` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `Terr` | 主城继承普通人族开局，工人 `SCV` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `Zerg` | 主城继承普通虫族开局，工人 `Drone` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `InfT` | `SICommandCenter` + `SISCV` | `RaceData.xml` | 是 |
| `TerH` | `HHCommandCenter` + `HHSCV` | `RaceData.xml` | 是 |
| `PZrg` | `DehakaHatchery` + `DehakaDrone` | `RaceData.xml` | 是 |
| `TerT` | `TychusCommandCenter` + `TychusSCV` | `Commanders/CommanderTychus.xml` | 是 |
| `ProZ` | `Nexus` + `Probe` | `Commanders/FutureCommanders.xml` | 特殊 SpawnRace，但主城/工人仍是普通 ID |

注意：`ProZ` 的专属性主要不靠私有 `Nexus/Probe`，而是靠泽拉图 commander 升级、顶栏、神器建筑、英雄和触发。

## 共享底座下如何区分单位和建筑

这批 `7v1` 外部数据的关键点，不是“每个指挥官都有一套完全私有的主基地和工人”，而是“共享 Catalog 壳 + 按玩家发放不同 commander 科技闭包”。

### 核心链路

```text
玩家选择码
-> PlayerCommanders commander ID
-> DefaultAbilityCommands / DefaultUpgrades
-> CommanderLevel / Prestige / Mastery / CampaignPerk
-> Build / Train / Research / Morph 的 Requirement
-> TechUnit.Commander 归属与分类
```

按运行时顺序看，主要是下面五层：

1. `LibKPVP.galaxy` 先把玩家绑定成某个 `PlayerCommanders` 实例。
   - 例如：`0008 -> ZergKerrigan`
   - 例如：`0014 -> ZergZagara`
2. `LibKCOR.galaxy` 的 `CC_ApplyCommanderTech` 再把这个 commander 的 `DefaultAbilityCommands` 和 `DefaultUpgrades` 发给该玩家。
   - 例如凯瑞甘会得到 `KerriganCommander`、`K5PrimalSlash`、`K5PsiStrike`
   - 例如扎加拉会得到 `ZagaraCommander`、`K5TwoDrones`、`MasteryZagaraLarvaRatePassive`
3. `CommanderLevel`、威望、精通、`CampaignPerk` 继续叠加到该玩家身上，影响按钮显示、升级状态、兵种分支和 UI。
4. 共享的 `Build/Train/Research` 壳本身会包含很多候选项，但能不能显示、能不能点击，要再过 `Requirement`。
5. `UserData.xml` 里的 `TechUnit -> Commander` 字段负责“这个单位/建筑算谁家的”，用于归属、索引和界面分类。

### 共享壳的直接证据

- 共享虫族建造壳 `ZergBuild` 里，同时放着：
  - `Build25 = ScourgeNest`
  - `Build27 = BileLauncherZagara`
- 共享虫族训练壳里，同时放着：
  - `LarvaTrain.Train12`，按钮要求 `HaveScourgeNest`
  - `LarvaTrainSwarm.Train30 = Scourge`，按钮要求 `HaveScourgeNest`
- 共享九头蛇研究壳 `HydraliskDenResearch` 里，同时放着凯瑞甘侧的研究项：
  - `Research5 = HotSHydraliskHealth`
  - `Research6 = HydraliskFrenzy`

这说明 `7v1` 的设计思路不是给每个 commander 复制一套完整虫族建筑/训练能力，而是在同一套壳里挂很多候选分支，然后用 commander 科技和需求链去裁剪。

### Commander 归属的直接证据

`TechUnit` 的 `Commander` 标签直接体现“归属”：

- `Hydralisk` 只挂 `ZergKerrigan`
- `Corruptor` 只挂 `ZergZagara`
- `Baneling` 只挂 `ZergZagara`
- `Zergling` 同时挂 `ZergKerrigan`、`ZergZagara`、`ZergStukov`
- `SpineCrawler` 同时挂 `ZergKerrigan`、`ZergZagara`、`ZergAbathur`
- `NydusNetwork` 只挂 `ZergKerrigan`、`ZergAbathur`

因此，共享底座下的“区分”不是靠基地 ID，而是靠“某个单位/建筑在 `TechUnit` 里被登记给哪些 commander”。

### Requirement 如何做运行时封锁

真正防止串兵种、串建筑、串升级的第二道封锁是 `Requirement`。

典型例子：

- `HaveHotSHydraliskHealth`
  - `Use = CountUpgradeHotSHydraliskHealthCompleteOnly...`
  - `Show = AndCountUpgradeKerriganCommanderCompleteOnlyLT5CountUpgradeCommanderLevelCompleteOnly`
  - 含义：这是凯瑞甘链的九头蛇升级，显示条件明确数 `KerriganCommander`
- `HaveHotSTissueAssimilation`
  - `Show = AndCountUpgradeKerriganCommanderCompleteOnlyLT12CountUpgradeCommanderLevelCompleteOnly`
- `HaveHotSBanelingCorrosiveBile`
  - `Show = AndCountUpgradeZagaraCommanderCompleteOnlyLTE11CountUpgradeCommanderLevelCompleteOnly`
  - 含义：这是扎加拉链的爆虫升级，显示条件明确数 `ZagaraCommander`
- `HaveHotSRupture`
  - `Show = AndCountUpgradeZagaraCommanderCompleteOnlyLTE11CountUpgradeCommanderLevelCompleteOnly`

底层节点也能看到这种 commander 计数方式：

- `CountUpgradeKerriganCommanderCompleteOnly`
- `CountUpgradeZagaraCommanderCompleteOnly`

所以，共享壳里的按钮并不是“谁都能看到再随便点”，而是运行时先给玩家打上某个 commander 的升级标记，再让 Requirement 去判断该玩家是否属于这条科技链。

### 一个建筑例子：ScourgeNest

`ScourgeNest` 的链路大致是：

```text
ZergBuild.Build25
-> Unit = ScourgeNest
-> Button Requirement = CanBuildScourgeNest
-> ScourgeNest 建成后
-> LarvaTrainSwarm.Train30 可训练 Scourge
-> Train30 Requirement = HaveScourgeNest
```

这里可以看出，共享壳并不妨碍“建筑决定单位”。它只是把这条链路写成：

- 建造按钮在共享壳里
- 建筑 ID 是独立的
- 后续单位按钮再数这个建筑是否存在

### 一个升级例子：凯瑞甘九头蛇 vs 扎加拉爆虫

这两条链能说明“同是虫族共享底座，为什么不会自动混在一起”：

- 凯瑞甘：
  - `Hydralisk` 在 `TechUnit` 里归属 `ZergKerrigan`
  - `HydraliskDenResearch` 有 `HotSHydraliskHealth`
  - `HaveHotSHydraliskHealth` 的显示条件数的是 `KerriganCommander`
- 扎加拉：
  - `Baneling` 在 `TechUnit` 里归属 `ZergZagara`
  - `HaveHotSBanelingCorrosiveBile`、`HaveHotSRupture` 的显示条件数的是 `ZagaraCommander`

也就是说，二者虽然共享了虫族基础壳，但升级分支已经被 commander 标记和需求链拆开了。

### 对当前 Mod 的启发

这套架构的优点是复用高，缺点是非常容易“串线”：

- 某个 `DefaultUpgrades` 发错了，可能整条科技链串给别的 commander
- 某个 `Requirement` 漏了 commander 判定，按钮可能会亮但点击无效，或者直接串兵种
- 某个 `TechUnit.Commander` 没登记或登记错了，文档归属、索引、界面分类就会乱

所以如果我们当前 Mod 继续走共享壳路线，必须把这三层一起闭包：

```text
PlayerCommanders / 默认升级能力
-> Requirement commander 判定
-> TechUnit.Commander 归属
```

缺任何一层，都会出现“看起来像这个指挥官，实际出的是公共兵种/公共建筑”的问题。

## 对当前 Mod 的提醒

如果目标是“所有指挥官单位都独立”，这份外部 Mod 的结论反而说明一个坑：

- `ZergKerrigan`、`ZergZagara`、`ZergAbathur` 不是通过私有 `SpawnRace` 拿私有基地。
- 它们能正常表现为合作指挥官，是因为外部包拥有官方合作数据闭包：默认升级、能力允许、单位/需求链、触发库、英雄/面板/幼虫逻辑一起生效。
- 当前 Mod 如果没有完整导入这些官方闭包，只把玩家设成 `Zerg` 或只给普通 Hatchery，就会回落成公共虫族基地和公共兵种。
- 要满足“每个指挥官单位都独立”，应为每个指挥官建立私有 `SpawnRace` 或地图初始化替换逻辑，并把主城、工人、幼虫、建筑建造、单位训练/变异、升级、技能按钮、效果、需求、威望/精通都指向该 commander 的私有链。

后续排查当前 Mod 时，建议固定使用这条闭包验证：

```text
Commander ID
-> PlayerCommanders.Race / SpawnRace
-> RaceData.StartingUnitArray[0/1]
-> 初始主城/工人是否为目标 commander 私有 ID
-> 主城/工人 AbilArray
-> Build/Train/Morph 按钮
-> Requirement
-> Effect
-> DefaultUpgrades / DefaultAbilityCommands
-> HeroUnit / HeroStructure / GlobalCastUnit
-> UI 初始化和 commander 专属触发
```
