# 7vs1 外部 Mod 指挥官信息整理

## 结论先行

这批外部数据的指挥官逻辑不是“每个指挥官都用私有基地和私有工人”。

它更接近官方合作指挥官的运行方式：先把玩家设置成某个 `PlayerCommanders` 实例，再按 `SpawnRace` 读取 Race Catalog 的开局单位，然后通过 `DefaultUpgrades`、`DefaultAbilityCommands`、英雄/全局施法单位、UI 分发和 `LibKMIS` 触发完成 commander 专属闭包。

因此，凯瑞甘、扎加拉、阿巴瑟在这批外部数据里 `SpawnRace` 都是普通 `Zerg`。它们的开局基地/工蜂不是私有 ID，而是普通虫族 Race 继承出来的开局主城和 `Drone`；专属性来自 `KerriganCommander`、`ZagaraCommander`、`AbathurCommander` 等默认升级和对应能力/需求链。如果我们当前 Mod 要求“每个指挥官单位都独立”，不能照搬这个外部 Mod 的 `SpawnRace=Zerg` 做法，必须给这些指挥官建立私有开局主城、工人、幼虫/变异能力和完整科技限制闭包。

### set_commander_for_player 做了什么

`libKPVP_gf_set_commander_for_player` 的关键动作：

| 步骤 | 逻辑 | 影响 |
| --- | --- | --- |
| 记录玩家 commander | `libKCOR_gf_CC_PlayerCommanderSet(player, commander)` | 写入 `ActiveCommanderForPlayer` |
| 设置出生种族 | `PlayerSetRace(player, libKCOR_gf_CC_CommanderSpawnRace(commander))` | 后续开局主城/工人按 `SpawnRace` 取 |
| 设置满级 | 固定 `lv_currentLevel = 15` | 当前外部 Mod 默认按满级处理 |
| 设置威望 | 读取玩家属性，设置威望索引 1/2/3 | 后续 `ApplyPrestigeTech` 生效 |
| 设置精通 | 三组选项映射到 0/30、5/25、...、60/60 | 写入对应 commander 的 `MasteryUpgrades` |
| 应用科技 | `libKCOR_gf_CC_ApplyTech(player)` | 应用军队、指挥官、等级、种族、威望、精通科技 |
| 额外解锁 | `libKPVP_gf_enable_upgrades_for_player` | 例如诺娃、雷诺、霍纳、蒙斯克的额外升级允许 |

### 开局主城和工人怎么来

`LibKPVP.galaxy` 的开局函数通过下面这条链取主城：

```text
ActiveCommanderForPlayer(player)
-> PlayerCommanders[commander].SpawnRace
-> RaceCatalog[SpawnRace].StartingUnitArray[0].Unit
```

代码证据是 `lv_townHallType = CatalogFieldValueGet(c_gameCatalogRace, libKCOR_gf_CC_CommanderSpawnRace(...), "StartingUnitArray[0].Unit", c_playerAny)`。

这意味着：

| SpawnRace | 当前可见开局 | 来源 | 是否私有 |
| --- | --- | --- | --- |
| `Prot` | 主城继承普通星灵开局，工人 `Probe` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `Terr` | 主城继承普通人族开局，工人 `SCV` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `Zerg` | 主城继承普通虫族开局，工人 `Drone` | `RaceData.xml` 只显式覆盖工人 index 1，主城从依赖继承 | 否 |
| `InfT` | `SICommandCenter` + `SISCV` | `RaceData.xml` | 是 |
| `TerH` | `HHCommandCenter` + `HHSCV` | `RaceData.xml` | 是 |
| `PZrg` | `DehakaHatchery` + `DehakaDrone` | `RaceData.xml` | 是 |
| `TerT` | `TychusCommandCenter` + `TychusSCV` | `Commanders/CommanderTychus.xml` | 是 |
| `ProZ` | `Nexus` + `Probe` | `Commanders/FutureCommanders.xml` | 特殊 SpawnRace，但主城/工人仍是普通 ID |

注意：`ProZ` 的专属性主要不靠私有 `Nexus/Probe`，而是靠泽拉图 commander 升级、顶栏、神器建筑、英雄和触发。

### 应用科技怎么串起来

## 对当前 Mod 的提醒

如果目标是“所有指挥官单位都独立”，这份外部 Mod 的结论反而说明一个坑：

- `ZergKerrigan`、`ZergZagara`、`ZergAbathur` 不是通过私有 `SpawnRace` 拿私有基地。
- 它们能正常表现为合作指挥官，是因为外部包拥有官方合作数据闭包：默认升级、能力允许、单位/需求链、触发库、英雄/面板/幼虫逻辑一起生效。
- 当前 Mod 如果没有完整导入这些官方闭包，只把玩家设成 `Zerg` 或只给普通 Hatchery，就会回落成公共虫族基地和公共兵种。
- 要满足“每个指挥官单位都独立”，应为每个指挥官建立私有 `SpawnRace` 或地图初始化替换逻辑，并把主城、工人、幼虫、建筑建造、单位训练/变异、升级、技能按钮、效果、需求、威望/精通都指向该 commander 的私有链。

后续排查当前 Mod 时，建议固定使用这条闭包验证：

```text
Commander ID
-> PlayerCommanders.Race / SpawnRace
-> RaceData.StartingUnitArray[0/1]
-> 初始主城/工人是否为目标 commander 私有 ID
-> 主城/工人 AbilArray
-> Build/Train/Morph 按钮
-> Requirement
-> Effect
-> DefaultUpgrades / DefaultAbilityCommands
-> HeroUnit / HeroStructure / GlobalCastUnit
-> UI 初始化和 commander 专属触发
```
