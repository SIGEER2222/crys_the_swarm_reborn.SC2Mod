## 本轮排查结论

### 1. 公共问题主因是地图层把合作指挥官真实单位壳替换错了

这轮最关键的发现是：多个地图把本应使用的合作模式英雄/指挥官单位壳，替换成了普通战役单位、空壳单位，或错误指挥官单位。

已确认的强证据包括：

- Kerrigan 线：地图曾把 `K5Kerrigan` 替成 `Kerrigan`
- Zeratul 线：地图曾把 `ZeratulCoop` 替成 `Zeratul`
- Swann 线：地图曾把 `SwannSwann` 替成 `Swann`

这类问题同时可能出现在：

- `MapScript.galaxy`
- 地图 `Objects`
- `Preload.xml`
- 地图初始化时的 squad / cargo helper 分支

因此，表现出来会像：

- 英雄模型不对
- 技能条不对
- 能攻击建筑但不能正常攻击单位
- 兵种 / 建筑 / 英雄表面有名字，但运行时实际创建的不是那套对象

### 2. 阿拉纳克还存在一次明确的本地数据错线

阿拉纳克不是纯脚本问题。旧错误版本里，`AlarakCoop` 的武器链曾接到错误对象：

- `DarkArchonChampionWeaponFunctional`
- `DarkArchonChampionWeaponFunctionalHoldPos`

源版本覆盖后的当前可工作数据，已恢复为：

- `AlarakAG`
- `AlarakAA`

这说明：**公共地图替换问题之外，个别指挥官自己的 UnitData / WeaponData 也可能被错误覆盖过。**

### 3. 源版本覆盖已证明“当前架构可以工作”

用户实测已经证明：把源版本数据覆盖回来后，英雄攻击与单位数据至少可以恢复正常。

因此后续推进原则应明确为：

- 不重新设计一套新架构
- 不重新大规模整包导入
- 以“当前源版本可工作对象”为真值
- 在此基础上做批量替换校正、地图初始化修正和统一回归

## 后续推进总策略

### 第一阶段：冻结可工作基线

目标：先把这次源版本覆盖后的可工作对象当作对照组，防止后续修图时再次把错误单位壳写回去。

本阶段动作：

1. 建一份“真实合作单位壳对照表”
2. 标出哪些单位是实际运行壳，哪些只是空壳或普通战役壳
3. 以后凡是地图脚本、Objects、Preload、helper 分支涉及这些对象，都先按对照表核对

当前已确认的高价值对照样例：

| 指挥官 | 正确运行壳 | 不应误替换成 |
|---|---|---|
| Kerrigan | `K5Kerrigan` | `Kerrigan` |
| Zeratul | `ZeratulCoop` | `Zeratul` |
| Swann | `SwannSwann` | `Swann` |
| Alarak | `AlarakCoop` | 错线武器链版本 |

### 第二阶段：优先收公共地图替换层

目标：先修“会同时影响多个英雄/指挥官”的公共问题，再回头补单个指挥官特性。

优先检查点：

1. 地图初始化强制写入的 `Ach/Commander`
2. `MapScript.galaxy` 中的英雄创建对象
3. 无基地图 / cargo 图调用的 helper 分支
4. `Objects` 中的预摆英雄、建筑、兵种对象
5. `Preload.xml` 中的单位预载对象

处理原则：

- 优先修对象 id 和初始化入口
- 优先恢复公共 helper 的正确分支
- 不在每张地图里复制一套新逻辑
- 单图临时补丁只作为过渡，不作为长期主路径

### 第三阶段：按指挥官收口本地机制

当公共层稳定后，再逐个处理：

- 英雄技能
- 顶栏技能
- 成长 / 威望 / 精通
- 特殊地图编队
- 训练链 / 科技链

### 第四阶段：统一 live 回归

最终验收不再只看“文件存在”或“Launcher 能选到”，而要同时确认：

1. 进图前 `CampaignXCore.SC2Bank` 的 `Ach/Commander` 正确
2. 开局基地 / 工人 / 第二单位正确
3. 英雄壳、技能条、训练链与该指挥官匹配
4. 特殊图不回落默认人族/星灵/异虫占位逻辑
5. 不再出现“攻击建筑有效、攻击单位无效”这类错壳症状

## 具体开发约束

后续版本推进时，必须遵守下面几条：

1. 不再把“看起来像对应角色的普通单位”当成合作英雄本体。
2. 不再只凭 `Launcher` 可见或 `UnitData` 有名字就判断接线正确。
3. 改地图前先确认真实运行壳、真实能力 id、真实初始化入口。
4. 修单图时同步检查 `MapScript.galaxy`、`Objects`、`Preload.xml` 和 `DocumentInfo`。
5. 新问题优先记为“公共替换层问题”或“个体机制问题”，不要重新回到“未移植”口径。
