# Alarak 2026-05-23 进度与问题总结

这份文档记录本轮对 Alarak 移植链路的有效结论、已确认问题、已完成修复和后续建议。

目的有两个：

1. 方便后续 AI 继续收口 Alarak。
2. 给其他指挥官移植提供可复用的排查思路。

## 本轮结论

### 1. 标准基地/农民“看起来没替换”并不等于 `CommanderAch` 错了

`XMCore.SC2Mod/Base.SC2Data/GameData/UserData.xml` 里的 `CommanderAch/Alarak` 当前仍是：

- `CommandCenter = Nexus`
- `Worker = Probe`
- `SecondUnit = Pylon`

这不是本轮的核心 bug。

Alarak 的塔达林化并不是靠 `CommanderAch` 直接换成独立的 `NexusTaldarim/ProbeTaldarim` 单位 ID，而是靠：

- `PlayerCommanders/ProtossAlarak` 的 `DefaultUpgrades`
- 其中的 `AlarakCommander`
- `CommanderSkin = TaldarimSkin`
- `CommanderLevel`

共同驱动。

因此如果 live 里看到普通星灵基地/探机，优先怀疑 runtime 没有把这些默认状态发给玩家，而不是先改 `CommanderAch`。

### 2. Alarak 的缺口核心在 runtime，不在数据本体

`XMAlarak.SC2Mod` 里阿拉纳克关键数据链本来就已经存在，包括：

- `AlarakCoop`
- `CoopCasterAlarak`
- `AlarakCommander`
- `TaldarimSkin`
- `AlarakEmpower`
- `DestructionWaveNoOffset`
- `AlarakKnockback`
- `AlarakACDeadlyCharge`

所以“技能不全 / 建筑没替换 / 农民没替换”这几个表象，本轮确认主要是 runtime 没把官方默认状态补齐。

### 3. 需要在 `XMFinal` 显式补 Alarak 的最小官方初始化链

本轮已在：

- `合作指挥官版起义狂潮/Mods/XM/XMFinal.SC2Mod/Base.SC2Data/LibE0EAE146.galaxy`

增加 `libE0EAE146_gf_ApplyAlarakCommanderRuntime()`，并在 `Initialize()` 中对 `Commander == "Alarak"` 调用。

当前这段 runtime 负责：

- 允许 `PlayerCommanders/ProtossAlarak` 的 `DefaultAbilityCommands`
- 发放 `PlayerCommanders/ProtossAlarak` 的 `DefaultUpgrades`
- 设置 `CommanderLevel = 15`
- 应用 `CommanderSkin = TaldarimSkin`

这一段是本轮最关键的修复。

live 已确认：

- 探机外观切成塔达林风格

这说明：

- 之后的主要焦点应转到技能、成长和地图 helper 的正式收口。

### 2. 技能链比之前完整

此前用户反馈“技能不全，应该还有两个”。

本轮确认后，问题拆成两层：

- 数据层：关键技能本来就存在
- runtime 层：需要先把 `CommanderLevel` 和默认状态发下去，否则显示/解锁条件不成立

live 截图里已经能看到阿拉纳克能力面板比之前更完整。

注意：这不等于“Alarak 全部技能显示问题已经百分之百收完”。  
后续仍应专门针对：

- 英雄选中后的完整命令卡
- `Empower`
- `DestructionWaveDistance`
- `LightningStrikes`
- `AreaDamageUpgrade`
- `AttackStun`

再做一次针对性核对。

### 3. 已定位并修正一处真实技能接线错误

`XMCore.SC2Mod/Base.SC2Data/GameData/UserData.xml` 中 `CommanderAch/Alarak` 的第 4 个升级映射，原先写的是：

- `AlarakLightningStrikes`

但 `XMAlarak` 实际用于英雄命令卡显示和效果校验的升级对象是：

- `AlarakSupplicantSacrificeLightningStrikes`

证据链如下：

- `RequirementData.xml` 的 `HaveAlarakLightningStrikes`
- `RequirementNodeData.xml` 的 `CountUpgradeAlarakSupplicantSacrificeLightningStrikesCompleteOnly`
- `UpgradeData.xml` 中存在 `AlarakSupplicantSacrificeLightningStrikes`
- `UpgradeData.xml` 中不存在 `AlarakLightningStrikes`

这个错配会导致：

- `AchBit` 发放的升级打不到实际 requirement
- 英雄命令卡对应的被动格可能不亮
- 后续排查容易误判成按钮或行为链缺失

本轮已把该映射改正，并同步修正：

- `scripts/import-official-alarak-data.ps1`
- `scripts/validate-alarak-port-fixed.ps1`

### 4. 已补齐 6 个 mastery 槽位与官方升级 ID 的对应关系

从本地官方导出 `references/official-casc-export/mods/starcoop/starcoop.sc2mod/base.sc2data/gamedata/userdata.xml` 可以直接核对到 Alarak 的 6 个 mastery 槽位：

1. `MasteryAlarakAutoAttackDamage`
2. `MasteryAlarakUnitAttackSpeed`
3. `MasteryAlarakEmpowerMeSlavesDuration`
4. `MasteryAlarakDeathFleetCDR`
5. `MasteryAlarakOverchargeShieldsDamage`
6. `MasteryAlarakChronoBoost`

此前 `XMCore` 中 `CommanderAch/Alarak` 的 `Poi` 映射里，除第 1 个外，其余名称都和实际导入升级 ID 不一致。  
这会导致：

- bank 中的点数无法命中真实 mastery upgrade
- `HaveMasteryAlarak*` requirement 永远不成立
- 顶栏 tooltip 追加项和相关被动展示失效

本轮已把 `Poi[0..5]` 全部改为上述真实官方升级 ID，并把静态校验一起补上。

## 本轮踩到的坑

### 1. `PlayerSetCommander` 在这里会报未授权

本轮一开始尝试在 `XMFinal` 的初始化里调用：

- `PlayerSetCommander(...)`

实机报错：

- `Calling 'PlayerSetCommander' is not authorized`

因此在当前战役 mod 运行环境里，不要照搬官方 `libcooc` 那条调用链。

本轮最终做法是：

- 保留 `DefaultAbilityCommands`
- 保留 `DefaultUpgrades`
- 保留 `CommanderLevel`
- 保留 `PlayerApplySkin`
- 删除 `PlayerSetCommander`

这是当前可用做法。

### 2. 不能把“标准基地单位 ID”误判成最终显示结果

Alarak 这一轮证明了：

- `CommanderAch` 里的 `Nexus / Probe / Pylon`
- 不代表 live 一定显示成普通星灵

外观、名称、部分按钮和皮肤可能由升级/skin/runtime 决定。

这条经验对其他指挥官也有参考价值：

- 先搞清楚“开局单位 ID”
- 再搞清楚“身份升级 / 皮肤 / 默认升级 / 指挥官等级”
- 不要看到 `CommanderAch` 还是基础单位名就立刻重做整套开局数据

### 3. 先静态分析，再少量 live

用户明确不希望频繁启动游戏打断工作。

本轮较有效的做法是：

1. 先查 `XMFinal` / `XMCore` / 指挥官模组的数据链
2. 先跑静态校验脚本
3. 最后只做一次或两次合并后的 batched live 验证

这个流程后续应保持。

## 当前仍未完成的 Alarak 项

### 1. 需要继续核对技能面板“最终应显示什么”

本轮已经证明 runtime 修复有效，但还需要明确区分：

- 哪些是主动技能按钮
- 哪些是被动图标
- 哪些是等级/升级后才显示
- 哪些应该在英雄命令卡显示
- 哪些应该在顶部面板显示

后续不要再用“应该还有两个”这种模糊描述，直接对照官方对象和实际 UI 槽位做表。

当前可先固定两条判断，避免继续跑偏：

- 顶栏主动技能按官方口径是 2 个：`Structure Overcharge`、`Death Fleet`
- 英雄命令卡则应包含主动技能 + 被动图标，不应把这两类槽位混为一谈

### 2. 需要继续收口地图分支里的 Alarak 正式编队

本轮之前已经把一些 helper 调整成更像 Alarak 的单位组合，但还没有完成最终收口。

后续应继续统一：

- 标准基地图
- 无基地图
- cargo 图
- 特殊落点图

尽量走统一 helper，减少每张地图硬编码。

### 3. 现存 `ScriptError` 不是这轮新引入的 Alarak runtime 问题，但需要后续处理

本轮最终 live 中剩余错误主要是地图级错误，包括：

- `Kit@ObserverSiegeMode`
- `gt_IntroFeederlingMover_Func`
- `gt_IntroCinematic_Func`

这几条在本轮最终修复后仍存在，说明：

- 它们不是 `PlayerSetCommander` 那条新引入错误
- 但它们仍会污染 live 验证环境

后续建议单独做“地图旧错误清理”，不要和 Alarak runtime 混在一起判责。

## 对其他指挥官可复用的经验

### 经验 1：先查 `PlayerCommanders`

如果某个指挥官出现：

- 外观不对
- 名称不对
- 基地/工人还是基础种族
- 技能栏不全

先查：

- `PlayerCommanders/<Commander>`
- `DefaultUpgrades`
- `DefaultAbilityCommands`
- `CommanderSkin`
- `CommanderData`

### 经验 2：先查 `CommanderLevel`

如果技能显示缺失，不要只看 `UnitData` 里有没有按钮。

还要查：

- `RequirementData`
- `RequirementNodeData`
- `CommanderLevel`
- 指挥官身份升级是否已发放

### 经验 3：官方 `libcooc` 逻辑不能整段照搬

官方合作逻辑里的某些 API 在当前战役 mod 环境不可直接用。  
本轮已经确认：

- `PlayerSetCommander` 会报未授权

因此后续移植要优先拆出“最小必要逻辑”，而不是整段复制。
