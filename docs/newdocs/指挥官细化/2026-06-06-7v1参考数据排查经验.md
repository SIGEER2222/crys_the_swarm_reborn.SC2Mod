# 7v1 参考数据排查经验

日期：2026-06-06

## 背景

排查 7v1 雷诺时，`TechUnit` 白名单显示 `Marauder` 属于 `TerranRaynor`，`BarracksTrain,Train4` 也能继承到官方 `Marauder` 训练能力。但实机观察是：兵营挂科技实验室后可以生产火蝠，却没有劫掠者。

这说明 7v1 的静态归属表、训练 Ability 和实际命令卡显示之间存在不一致。以后不能只凭 `TechUnit` 或 `Ability` 命中就判断“该指挥官实际可造”。

## 本次结论

7v1 雷诺的 `Marauder` 应标记为：

- `TechUnit` 归属：命中 `TerranRaynor`。
- `Ability` 训练链：`BarracksTrain,Train4 -> Marauder` 存在，且继承官方 `HaveAttachedTechLab` 条件。
- 实际命令卡闭包：不成立或至少未验证通过。
- 实机口径：不能按“7v1 雷诺兵营实际可造劫掠者”记录。

更精确的写法是：

| 项 | 状态 |
|---|---|
| 裸兵营训练劫掠者 | 否 |
| 兵营 + 科技实验室训练劫掠者 | 实机未显示，不能算正向闭包 |
| 火蝠 | 7v1 有明确命令卡入口，实机可见 |
| 劫掠者 | 白名单和 Ability 存在，但命令卡覆盖存在问题 |

## 后续排查规则

以后使用 7v1 作为参考时，按下面顺序判断一个单位是否真能算“指挥官可造”：

1. 先看官方数据源确认该单位是否属于该指挥官。
2. 再看 7v1 `TechUnit.Commander`，只能作为归属白名单，不是最终结论。
3. 再看生产建筑 `UnitData.CardLayouts` 是否有完整按钮：`Face`、`Type`、`AbilCmd`、`Row`、`Column`。
4. 再看 `AbilData` 的 `InfoArray` 是否实际产出目标单位，并记录 `Requirement`。
5. 再看 `Requirement` 是否会被当前指挥官、当前等级、当前威望、当前建筑状态满足。
6. 最后用实机或调试日志确认按钮可见、可点击、产出单位正确。

只有同时通过 `UnitData -> AbilData -> Requirement -> 实机表现` 的链路，才可写成正向闭包。

## 禁止再犯的判断

不要再把下面几类命中直接写成“可造”：

- `TechUnit` 白名单命中，但命令卡按钮缺失。
- `AbilData` 有训练项，但命令卡没有有效入口。
- 命令卡有 `Face`，但缺 `Type/AbilCmd/Row/Column` 或被后续包覆盖。
- 共享 Catalog 壳里出现按钮，但该按钮实际属于 Nova、Swann、Horner、Mengsk 等其他人族指挥官。
- 官方继承链里有单位，但 7v1 后续包覆盖了对应 LayoutButton。

## 对当前 Mod 的启发

当前 Mod 不应照抄 7v1 的共享命令卡写法。当前目标是每个指挥官单位独立，因此应优先使用私有生产链：

```text
私有生产建筑 -> 私有 Train Ability -> 私有 Unit 输出 -> 私有形态/技能/升级闭包
```

如果确实参考 7v1，也只能参考它的运行时思路，不能把 7v1 的 `TechUnit` 白名单或共享按钮壳直接当实现依据。
