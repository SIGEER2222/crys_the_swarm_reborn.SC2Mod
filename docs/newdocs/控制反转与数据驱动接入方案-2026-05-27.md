# 控制反转与数据驱动接入方案

日期：2026-05-27

## 目标

把当前“地图和科技建筑里到处判断指挥官/兵种”的实现，逐步改成数据驱动的控制反转模式。

补充修订：在整理完整指挥官精通、威望和兵种闭包后，架构需要新增独立的“强度融合层”。详细回看见：

```text
docs/指挥官/架构回看-精通威望与兵种整理后修订-2026-05-27.md
```

目标不是在 SC2 / Galaxy 里模拟完整 OOP，而是达到下面效果：

1. 地图脚本只表达任务场景，不关心具体指挥官。
2. `XMFinal.SC2Mod` 作为唯一战役运行时分发入口。
3. 指挥官声明自己的开局、无基地、运输、奖励、空军支援等初始化方案。
4. 兵种声明自己需要的攻防升级、科技升级、按钮、需求和所属科技建筑。
5. 科技建筑只作为承载容器，不维护所有兵种规则。
6. 新指挥官和新兵种主要通过补 profile 与少量 hook 接入，而不是改每张地图和每个科技建筑。

## 当前问题

### 地图初始化问题

当前容易出现以下模式：

```galaxy
if (commander == "Abathur") {
    ...
}
else if (commander == "Kerrigan") {
    ...
}
else if (commander == "Alarak") {
    ...
}
```

这会导致：

- 新增一个指挥官要改多张地图。
- 同一类开局逻辑在标准基地图、无基地图、运输图、奖励图里重复。
- Launcher 能显示指挥官，但地图运行时未必真的接通。
- 地图成为玩法逻辑 owner，和 `XMFinal` 统一 runtime owner 的目标冲突。

### 科技建筑问题

当前科技建筑容易承担过多职责：

- 知道哪些单位存在。
- 知道哪些单位吃哪些攻防。
- 知道每个单位有哪些专属科技。
- 知道按钮、需求、研究能力和升级项的排列。

这会导致：

- 新增单位时需要改多个建筑。
- 攻防和专属科技规则分散在 XML、触发器、按钮、需求之间。
- 难以验证某个单位的科技链是否完整。

## 总体设计

采用“数据注册 + 运行时分发 + 生成工具”的三层方案。

```text
指挥官/兵种 Profile
  -> 生成或同步 SC2 XML Catalog
  -> XMFinal 统一读取/分发
  -> 地图只调用场景 helper
```

### 1. 数据注册层

新增或扩展 `UserData.xml` 里的 profile。

建议不要直接塞进已有 `CommanderAch` 的所有字段里。`CommanderAch` 保留等级、精通、基础 commander 信息；新的初始化与科技声明使用独立 UserData 类型，减少历史兼容风险。

建议类型：

```text
CommanderRuntimeProfile
CommanderScenarioLoadout
CommanderPowerFusionProfile
CommanderLevelUnlockProfile
CommanderMasteryProfile
CommanderPrestigeEffectProfile
CommanderRosterProfile
CommanderUnitTechProfile
CommanderTechBuildingProfile
```

其中：

- `CommanderPowerFusionProfile`：声明等级满级、精通全满、威望正面融合的执行策略。
- `CommanderLevelUnlockProfile`：声明 15 级解锁项和满级后 roster 变化，避免旧 8 槽 `CommanderAch.Upg` 表达不完整。
- `CommanderMasteryProfile`：声明 6 项精通按 30 点应用，并标记是否需要 runtime hook。
- `CommanderPrestigeEffectProfile`：把官方威望拆成正面效果、负面代价、禁用项、补偿项和待审计项。
- `CommanderRosterProfile`：声明测试台和全单位展示需要生成/验证的建筑、单位、英雄、面板和特殊形态，并区分 `initial`、`level15`、`power_fusion` 三阶段。

### 2. 运行时分发层

`XMFinal.SC2Mod` 增加一组统一 helper。

建议入口：

```galaxy
XM_InitCommanderStandardBase(player, point)
XM_CreateCommanderScenarioSquad(player, point, scenarioKind)
XM_CreateCommanderCargoSquad(container, scenarioKind)
XM_InitCommanderPanel(player)
XM_ApplyCommanderPowerFusion(player, commander)
XM_RunCommanderHook(player, hookKind)
```

当前第一步已经在 `原始mod/Mods/XM/XMFinal.SC2Mod/Base.SC2Data/LibE0EAE146.galaxy` 落地为兼容旧地图的 adapter：

```text
libE0EAE146_gf_Initialize(bool)
  -> PrepareCommanderFromBank 或测试 override
  -> Initialize_Legacy

libE0EAE146_gf_InitializeBase(point, int, point, bool)
  -> ApplyCommanderProgression
  -> CreateBaseStructures
  -> CreateStartingWorkers
  -> CreateSecondUnit
  -> RunCommanderBaseHook
```

这一步还没有把各指挥官 hook 拆进独立文件，但已经把原来一整块 `InitializeBase` 拆成可替换阶段。后续 Raynor、Nova、Abathur 可以先从 `RunCommanderBaseHook` 中抽 profile/hook，逐步把 commander if/else 从 `XMFinal` 的集中分发迁移到独立声明。

Raynor 试点已先落地在 `XMFinal`：

```text
XMTestBench_RunRoster
  -> NormalizeCommanderId
  -> XMTestBench_RaynorRoster
  -> XMTestBench_CreateProfileUnit

XM_InvokeCommanderPanelAbility
  -> NormalizeCommanderId
  -> XMTestBench_RaynorPanelCostSmoke
```

这条路径还不是最终的数据文件驱动形态，但已经把第一批差异收敛到指挥官 profile helper，而不是写在 `CommanderTestBench.SC2Map` 里。后续可把 Raynor helper 中的清单迁移到 `CommanderRosterProfile` / `CommanderPanelProfile`，再让 Nova、Abathur 复用同一套创建和日志函数。

地图层只传场景语义：

```text
standard_base
no_base_light
no_base_heavy
no_base_hero
cargo_light
cargo_heavy
cargo_air
bonus_reward
air_support
replacement_squad
```

### 3. 生成工具层

科技树和按钮链不建议全部运行时动态拼。SC2 的 command card、Ability、Button、Requirement、Upgrade 大多是静态 Catalog 数据，最稳做法是：

1. 兵种在 profile 中声明科技需求。
2. 工具读取 profile。
3. 工具生成或更新：
   - `AbilData.xml`
   - `ButtonData.xml`
   - `RequirementData.xml`
   - `UpgradeData.xml`
   - `UnitData.xml`
   - `GameStrings.txt`
4. 静态校验脚本检查断链。

优先复用现有能力：

- `tools/Sc2ModTool`
- `scripts/sc2mod-edit.ps1`
- `scripts/mod-index.ps1`
- `scripts/validate-*-port.ps1`
- `scripts/validate-*-tech-chain.ps1`

## 指挥官初始化控制反转设计

### Profile 字段建议

`CommanderRuntimeProfile`：

```text
Id
Commander
CommandCenter
Worker
SecondUnit
CasterUnit
PanelInit
StartHook
PostInitHook
HeroUnit
HeroCreateMode
UsesBiomass
UsesTopPanel
DefaultRace
```

`CommanderScenarioLoadout`：

```text
Id
Commander
ScenarioKind
Unit
Count
CreateMode
ApplyFullBiomass
CargoMode
RequirementUpgrade
FallbackScenarioKind
```

含义：

- `ScenarioKind`：地图传入的抽象场景。
- `Unit` / `Count`：该指挥官在该场景下生成什么。
- `CreateMode`：普通创建、无视碰撞创建、货舱创建、替换创建等。
- `ApplyFullBiomass`：阿巴瑟这类机制用，不让地图知道生物质细节。
- `FallbackScenarioKind`：没有终极单位或特殊升级时回退到另一套 loadout。

### 运行时调用方向

地图中原本类似：

```galaxy
if (commander == "Abathur") {
    CreateAbathur...
}
else if (commander == "Kerrigan") {
    CreateKerrigan...
}
```

改成：

```galaxy
libE0EAE146_gf_CreateCommanderScenarioSquad("no_base_heavy", 1, Point...);
```

`XMFinal` 内部流程：

```text
读取当前 commander
读取 CommanderScenarioLoadout[commander, scenarioKind]
若不存在则读取 fallback
逐条创建单位
按 profile 标记执行特殊附加逻辑
最后运行 commander hook
```

### Hook 边界

Galaxy 没有真正的接口、多态和动态函数调用，因此 hook 不能无限拆散。

允许存在一个集中 dispatcher：

```galaxy
XM_RunCommanderHook(commander, hookKind, player)
```

内部可以保留少量分支：

```galaxy
if (commander == "Abathur") {
    XM_Abathur_RunHook(hookKind, player);
}
else if (commander == "Dehaka") {
    XM_Dehaka_RunHook(hookKind, player);
}
```

这个分支只允许存在于 `XMFinal` 或公共指挥官运行时库，不允许散落到地图。

适合放 hook 的内容：

- 阿巴瑟生物质初始化。
- 德哈卡吞噬/精华类系统。
- 泰凯斯小队/酒馆类系统。
- 斯台特曼卫星/姿态类系统。
- 泽拉图神器碎片类系统。
- 诺娃首个生产建筑、形态切换和超级隐形类运行时状态。
- 雷诺空军人口影响顶部面板充能这类无法纯 Catalog 表达的威望收益。

不适合放 hook 的内容：

- 标准基地单位。
- 普通开局小队。
- 普通运输舱单位。
- 攻防升级归属。
- 科技按钮文本。
- 等级 15 全解锁和 6 项精通全满的基础应用。
- 官方威望负面效果的跳过规则。

这些应由 profile 解决。

### 攻防升级声明

不要让科技建筑判断某单位吃什么攻防。

兵种自己声明：

```text
Hydralisk:
  WeaponUpgradeGroup = ZergMissile
  ArmorUpgradeGroup = ZergGroundArmor
```

工具展开为：

- 对应 `UpgradeData.xml` 的 affected unit/weapon/effect 修改。
- 对应按钮和研究能力。
- 对应 requirement。

### 专属科技声明

兵种自己声明专属科技：

```text
Hydralisk:
  ResearchBuilding = HydraliskDen
  ResearchUpgrade = GroovedSpines
  ResearchButton = ResearchGroovedSpines
  Requirement = HasHydraliskDen
```

如果一个指挥官要把科技放到统一科技建筑，例如 `EvolutionChamber`，则由 profile 指定：

```text
Commander = Abathur
Unit = Hydralisk
ResearchBuilding = EvolutionChamber
ResearchAbility = EvolutionChamberResearch
```

建筑只声明自己能承载哪些类型，不声明具体单位清单。

### 生成策略

第一阶段不直接重写所有 XML。建议先生成审计报告和 patch。

工具流程：

```text
读取 UnitTechProfile
读取当前 XML 索引
校验 Unit / Button / Upgrade / Requirement 是否存在
生成缺口报告
生成 patch
人工或脚本 apply
运行 validate
```

后续成熟后再做到自动 apply。

## 单位演化与替换设计

单位“升级成另一种单位”要先区分类型，不要全部用触发器 `ReplaceUnit` 解决。

### 演化类型

建议把演化分成四类：

| 类型 | SC2 机制 | 适用场景 | 优先级 |
|---|---|---|---|
| `morph` | `CAbilMorph` | 单位/建筑直接变形，例如基地升级、架起/收起、监察王虫等 | 高 |
| `trainMorph` | `CAbilTrain` + `MorphUnit` | 进化成茧/中间单位，再完成为目标单位，例如阿巴瑟终极进化 | 高 |
| `upgradeVariant` | `UpgradeData` 修改字段 | 不换单位 id，只改属性、技能、武器、行为 | 高 |
| `triggerReplace` | Galaxy `ReplaceUnit` | 地图已有单位按 commander 替换、历史兼容、特殊剧情替换 | 低 |

原则：

1. 官方原本是 `CAbilMorph` / `CAbilTrain` 的，优先保留 catalog 机制。
2. 只是属性增强，不要换单位，使用 `UpgradeData`。
3. 地图开局阵容替换属于场景初始化，不属于单位演化。
4. `ReplaceUnit` 只作为兼容层，不能成为新增演化的默认方案。

### Profile 字段建议

新增 `CommanderUnitEvolutionProfile`：

```text
Id
Commander
SourceUnit
TargetUnit
EvolutionKind
Ability
AbilityCommand
Button
Requirement
UnlockUpgrade
ResearchUpgrade
MorphUnit
CocoonUnit
FinishEffect
CancelEffect
Time
CostMinerals
CostVespene
CostSupply
PreserveVitals
PreserveEnergy
PreserveCargo
PreserveControlGroup
PreserveCustomValues
PostEvolutionHook
FallbackUnit
```

字段含义：

- `SourceUnit`：原单位。
- `TargetUnit`：最终目标单位。
- `EvolutionKind`：`morph` / `trainMorph` / `upgradeVariant` / `triggerReplace`。
- `Ability` / `AbilityCommand`：执行演化的能力和命令。
- `Button`：命令卡按钮。
- `Requirement`：显示和可用条件。
- `UnlockUpgrade`：等级、精通或科技解锁。
- `MorphUnit` / `CocoonUnit`：中间单位或茧。
- `Preserve*`：演化后需要保留的状态。
- `PostEvolutionHook`：特殊 commander 机制补偿，例如生物质、精华、英雄等级。

### 状态保留规则

不同机制的状态保留能力不同：

1. `CAbilMorph` 通常最适合保留单位连续性。
2. `CAbilTrain + MorphUnit` 适合需要中间茧、进化时间和完成提示的单位。
3. `ReplaceUnit` 容易丢失选择、控制组、自定义值、行为层数和部分运行时状态。
4. 特殊状态必须显式声明和验证。

需要重点保留的状态：

```text
生命值比例
能量
护盾
经验/等级
生物质层数
精华层数
控制组
货舱
buff/debuff
冷却时间
玩家归属与同盟关系
```

如果状态无法由原生 morph 保留，则由 `PostEvolutionHook` 处理。

示例：

```text
Abathur:
  SourceUnit = RoachVile
  TargetUnit = Brutalisk
  EvolutionKind = trainMorph
  Ability = EvolveToBrutalisk
  MorphUnit = BrutaliskCocoon
  Requirement = BrutaliskMorphAvailable
  PreserveCustomValues = Biomass
  PostEvolutionHook = AbathurApplyBiomassAfterEvolution
```

### 演化链验证

每条演化链必须能追到：

```text
SourceUnit
  -> Ability
  -> AbilityCommand / InfoArray
  -> Button
  -> Requirement
  -> UnlockUpgrade
  -> MorphUnit / CocoonUnit
  -> TargetUnit
  -> Actor / Model / Sound
```

缺一项都不算闭环。

建议新增脚本：

```text
scripts/sc2/validate-unit-evolution-profiles.ps1
```

检查项：

1. `SourceUnit` 和 `TargetUnit` 存在。
2. `Ability` 类型符合 `EvolutionKind`。
3. `Button` 存在并有文本。
4. `Requirement` 存在且引用的升级存在。
5. `MorphUnit` / `CocoonUnit` 存在。
6. `TargetUnit` 的能力、武器、Actor、模型、声音完整。
7. 演化后目标单位仍属于正确攻防升级组。
8. 特殊状态保留项有 hook 或明确声明不保留。

### 演化日志

演化链应补充 `[XM_DBG]` 事件：

```text
[XM_DBG][INFO][EVOLUTION_REQUEST] commander=Abathur source=RoachVile target=Brutalisk kind=trainMorph ability=EvolveToBrutalisk
[XM_DBG][INFO][EVOLUTION_START] source=RoachVile morphUnit=BrutaliskCocoon player=1
[XM_DBG][INFO][EVOLUTION_DONE] target=Brutalisk player=1 preserve=Biomass result=ok
[XM_DBG][ERROR][EVOLUTION_MISSING] source=RoachVile field=Requirement id=BrutaliskMorphAvailable
```

## 单位技能、能力、属性接入设计

单位接入不能只看 `UnitData.xml` 里有没有单位 id。一个可玩的单位至少包含能力、按钮、需求、效果、行为、武器、Actor、模型、声音、本地化和升级归属。

### 单位能力 Profile

新增 `CommanderUnitAbilityProfile`：

```text

CardColumn
DefaultAutocast
DefaultEnabled

Cooldown
TargetFilters

Validator

PostCastHook
```

`AbilityKind` 建议枚举：

```text

autocast
morph
train
research
build
transport
topPanel
```

原则：

1. Profile 只声明“这个单位应该拥有这个能力及其接入口”。
2. 具体伤害、范围、搜索、buff、冷却等仍由 XML catalog 承载。
3. 工具负责检查 profile 引用的 catalog 链是否完整。
4. 不要把复杂技能效果写进地图触发器。

### 单位属性 Profile


注意：

- 这个 profile 不建议重复维护生命、攻击、护甲的具体数值。
- 具体数值仍以 `UnitData.xml` / `WeaponData.xml` / `BehaviorData.xml` / `UpgradeData.xml` 为准。
- Profile 负责声明归属和验证规则，例如“这个单位吃哪个攻防组”“是不是英雄”“是不是空军”。

### 能力接入链路

每个主动技能至少要闭合：

```text
UnitData.AbilArray
  -> AbilData
  -> AbilityCommand / CmdButtonArray
  -> ButtonData
  -> RequirementData
  -> EffectData
  -> BehaviorData / ValidatorData
  -> ActorData / ModelData / SoundData
  -> LocalizedData
```

每个被动技能至少要闭合：

```text
UnitData.BehaviorArray
  -> BehaviorData
  -> EffectData / ValidatorData
  -> ButtonData 或 tooltip
  -> UpgradeData 解锁或增强
  -> LocalizedData
```

每个武器至少要闭合：

```text
UnitData.WeaponArray
  -> WeaponData
  -> EffectData
  -> Damage/Search/Set/Switch
  -> ActorData attack actor
  -> SoundData / ModelData
```

### 能力接入方式

优先级：

1. 官方完整 catalog 链导入到 `XM<Commander>.SC2Mod`。
2. 用 profile 声明单位拥有关系和命令卡位置。
3. 用生成工具补 `AbilArray`、`CardLayouts`、按钮、需求。
4. 用静态脚本验证 effect / behavior / actor / text 断链。
5. 只有运行时状态类能力才进入 `XMFinal` hook。

不推荐：

- 在地图里临时给单位加技能。
- 用触发器模拟本来能由 `EffectData` / `BehaviorData` 完成的技能。
- 把技能按钮写死在科技建筑或地图脚本里。

### 属性和升级关系

属性变化分三类：

| 类型 | Owner | 示例 |
|---|---|---|
| 基础属性 | `UnitData` / `WeaponData` / `BehaviorData` | 生命、护甲、速度、武器周期 |
| 科技增强 | `UpgradeData` | 加射程、加生命、解锁技能 |
| 运行时状态 | `BehaviorData` / Galaxy hook | 生物质、精华、英雄等级、临时 buff |

规则：

1. 基础属性不要写入 profile。
2. profile 只写升级组和验证意图。
3. 攻防/科技增强由 `CommanderUnitTechProfile` 和 `UpgradeData` 负责。
4. 生物质、精华这类动态属性由 commander hook 负责，但必须有日志。

### 单位完整接入验收

一个单位完成接入应满足：

1. 单位能被训练、创建或演化出来。
2. 命令卡上技能按钮位置正确。
3. 主动技能能释放。
4. 被动技能或行为实际生效。
5. 武器能攻击正确目标。
6. 攻防升级能影响该单位。
7. 专属科技能解锁或增强该单位。
8. 演化后仍保留应保留的状态。
9. 本地化文本不缺失。
10. 日志能看到能力接入和演化链验证结果。

建议新增脚本：


## 英雄单位技能接入与官方一致性

英雄单位的技能不能按“头像选中了哪个指挥官，就在触发器里给单位塞几个按钮”来做。SC2 的技能实际接入口在 Catalog：英雄 `UnitData` 挂 `AbilArray`、`BehaviorArray`、`WeaponArray`，命令卡 `CardLayouts` 决定玩家看到的按钮；`AbilData` 再继续引用按钮、需求、效果、行为、校验器、Actor、模型、声音和文本。

因此英雄技能接入应按“英雄技能闭包”处理，而不是只同步英雄名或技能名。

### 数据源分工

本仓库当前要区分三层来源：

```text
游戏数据/官方合作指挥官/commanders/<Commander>/
references/sc2-build-96883-casc-export/
原始mod/Mods/XM/XM<Commander>.SC2Mod/Base.SC2Data/GameData/
合作指挥官版起义狂潮/Mods/XM/
```

### 当前数据源优先级修正

截至 2026-05-28，当前本地有两条工程线：`原始mod/` 是拿原 mod 续上的新项目和当前实现/回归线；`合作指挥官版起义狂潮/` 仍属于半成品旧测试产物，之前测试尚未成功。后续设计精通、威望、等级加点和官方一致性时，不要把半成品旧线当成可信来源。

优先级改为：

1. `游戏数据/官方合作指挥官/commanders/<Commander>/`：用于确定官方等级、精通、威望、默认升级和能力命令。
2. `references/sc2-build-96883-casc-export/`：用于追官方 Catalog、UserData、本地化、触发器和完整效果闭包。
3. `原始mod/`：当前实现/回归目标，承载拿原 mod 续上的新项目；可作为当前接入状态依据，但不作为官方基准。
4. `合作指挥官版起义狂潮/`：只能作为半成品旧实现参考，除非某个链路已经被单独验证成功，否则不能反推设计结论，也不要直接混入当前实现线。

因此，后续文档如果写“当前运行数据”或引用 `XMFinal`、`XMCore`、`XM<Commander>`，必须明确这是待验证实现线索，不是官方数据依据。

`游戏数据/官方合作指挥官` 的职责：

1. 确认官方合作指挥官有哪些英雄单位。
2. 确认默认升级、默认能力命令、威望、精通、等级加点。
3. 给 profile 生成提供 commander 口径和解锁线索。

`references/sc2-build-96883-casc-export` 的职责：

1. 作为官方合作指挥官数据基准。
2. 当目标是“和暴雪合作模式一致”时，优先从这里追官方 Catalog、UserData 和本地化。
3. 用于校验 `原始mod` 和当前 mod 是否已经偏离官方。

例如：

- `commanders/Tychus/heroes.json` 列出泰凯斯和 8 个亡命徒英雄。
- `commanders/Tychus/commander.json` 给出 `TychusCommander` 默认升级，以及 `TychusFakeReviveTrain` 的默认能力命令。
- `commanders/Dehaka/heroes.json` 列出 `DehakaCoop`、`DehakaGlevig`、`DehakaMurvar`、`DehakaDakrun`。
- `commanders/Dehaka/commander.json` 给出 `DehakaCommander`、`SwarmHostFakeWeapon` 默认升级。

`原始mod` 的职责：

1. 作为当前实现/回归线，承载从原 mod 续上的新项目。
2. 承载当前 `XMFinal.SC2Mod`、测试台、回归脚本和已接入的 Catalog/runtime 链路。
3. 提供可验证的按钮位置、技能命令、需求、效果、行为、Actor、模型、声音和触发逻辑。
4. 帮助判断哪些链路在移植时容易漏掉。

`合作指挥官版起义狂潮/Mods/XM` 的职责：

1. 作为半成品旧测试线索。
2. 仅在明确标注为“旧线索/待验证参考”时用于对照目录、命名、按钮或历史尝试。
3. 不作为当前实际 runtime owner，不作为当前开发目标，不直接证明玩法已验证。

结论：`游戏数据/官方合作指挥官` 不能单独还原英雄技能，只能作为“官方身份和解锁口径”。`原始mod` 是当前实现/回归线，但不能当成官方基准。要做到“和游戏里的合作指挥官一致”，官方口径以 `references/sc2-build-96883-casc-export` 为准；实际接入要落到当前 `原始mod/Mods/XM` 的 runtime、Catalog 和面板链路。

### 英雄技能闭包

一个英雄主动技能至少要闭合：

```text
Hero UnitData
  -> AbilArray
  -> CardLayouts / LayoutButtons
  -> AbilData
  -> AbilityCommand / CmdButtonArray
  -> ButtonData
  -> RequirementData
  -> EffectData
  -> BehaviorData / ValidatorData
  -> ActorData / ModelData / SoundData
  -> LocalizedData
```

一个英雄被动或光环至少要闭合：

```text
Hero UnitData
  -> BehaviorArray 或 CAbilBehavior
  -> BehaviorData
  -> EffectData / ValidatorData
  -> ButtonData / Tooltip
  -> UpgradeData / RequirementData
  -> LocalizedData
```

一个英雄升级/学技能链至少要闭合：

```text
Hero UnitData.CardLayouts
  -> Learn/Research ability
  -> AbilData InfoArray
  -> ButtonData
  -> RequirementData
  -> UpgradeData 或 ability level
  -> 被解锁的 AbilData / BehaviorData / EffectData
```

运行时只负责“什么时候创建英雄、什么时候给点数、什么时候刷新状态、什么时候记录日志”。技能本身的伤害、范围、冷却、目标过滤、buff、模型和音效应尽量留在 Catalog。

1. 英雄单位 id 和 parent 链。
2. 命令卡按钮位置。
3. `AbilData` 类型和 command。
4. `RequirementData` 解锁条件。
5. `EffectData` 根效果和递归子效果。
6. `BehaviorData` buff/debuff/aura。
7. `ValidatorData` 目标过滤和显示条件。
8. `ActorData`、`ModelData`、`SoundData` 表现资源。
9. `UpgradeData` 对技能的增强。
10. `progression/prestige/mastery` 是否影响同一批技能。

## 诺娃形态切换、武器与特性接入

诺娃是英雄接入里比较容易踩坑的类型。她不是简单“换一个模型”，也不是普通的 `UnitMorph` 变成另一个单位；当前 `合作指挥官版起义狂潮` 里的实现更接近一套状态机：

```text
英雄单位 NovaCoop
  -> CAbilBehavior NovaKitSwap 切换形态
  -> Behavior NovaCombatSuit / NovaPermanentlyCloaked 改状态
  -> WeaponData / EffectData 改攻击方式和伤害分支
  -> Requirement / Validator 决定按钮显示、技能可用性
  -> ActorData 监听 Behavior.On/Off 改 wireframe、队伍头像、动画组、语音
```

### 当前 mod 的实际链路

当前运行侧以这些文件为准：

```text
合作指挥官版起义狂潮/Mods/XM/XMNova.SC2Mod/Base.SC2Data/GameData/UnitData.xml
合作指挥官版起义狂潮/Mods/XM/XMNova.SC2Mod/Base.SC2Data/GameData/AbilData.xml

合作指挥官版起义狂潮/Mods/XM/XMNova.SC2Mod/Base.SC2Data/GameData/WeaponData.xml

合作指挥官版起义狂潮/Mods/XM/XMNova.SC2Mod/Base.SC2Data/GameData/ActorData.xml
```

`NovaCoop` 自身挂了形态切换能力：

```text
UnitData.xml
NovaCoop
  AbilArray Link="NovaKitSwap"
  BehaviorArray Link="NovaPermanentlyCloaked"
  WeaponArray Link="NovaWeaponImprovedCanisterRifle"
  CardLayouts:
    NovaSwitchAssaultMode -> NovaKitSwap,On
    NovaSwitchStealthMode -> NovaKitSwap,Off
```

`NovaKitSwap` 是 `CAbilBehavior`：

```text
AbilData.xml
CAbilBehavior id="NovaKitSwap"
  Flags Toggle=1
  Cost Cooldown Link="Abil/NovaSuitSwap" TimeUse=45
  OffCost Cooldown Link="Abil/NovaSuitSwap" TimeUse=45
  BehaviorArray value="NovaCombatSuit"
```

也就是说：

1. 默认形态是潜行形态，`NovaCoop` 出生时带 `NovaPermanentlyCloaked`。
2. 点 `NovaKitSwap,On` 时，能力给诺娃加 `NovaCombatSuit`。
3. 点 `NovaKitSwap,Off` 时，toggle 关闭，`NovaCombatSuit` 被移除。
4. `NovaCombatSuit` 的开启/关闭再带出一串行为、武器、效果、UI 和演员事件。

### 形态如何改变攻击方式

当前 mod 对攻击方式的处理有两层。

第一层是形态本身：

```text
BehaviorData.xml
NovaPermanentlyCloaked
  Modification.StateFlags[Cloak] = 1

NovaCombatSuit
  Modification.MoveSpeedMultiplier = 1.311
  Modification.BehaviorLinkDisableArray = NovaPermanentlyCloaked
  Modification.WeaponArray = HellfireShotgunNova
  Modification.WeaponDisableArray = NovaWeaponImprovedCanisterRifle
  InitialEffect = NovaCombatSuitInitialSet
  FinalEffect = NovaStealthSuitInitialSet
```

所以突击形态不是“仅显示突击按钮”。它会禁用永久隐形、加入霰弹枪武器、禁用狙击步枪武器，并触发切换进入/离开的效果。

第二层是武器/装备行为：

```text
EffectData.xml
NovaRemoveAllEquippedWeapon
  BehaviorCategories[User9] = 1

NovaWeaponImprovedCanisterRifleABSet
  NovaRemoveAllEquippedWeapon
  NovaWeaponImprovedCanisterRifleAB

NovaWeaponHellfireShotgunABSet
  NovaRemoveAllEquippedWeapon
  NovaWeaponHellfireShotgunAB
```

官方合作模式里 `NovaEquipmentSwap` 是完整的 `CAbilSpecialize`，用 `Specialize1/2/5...` 触发这些 `ABSet` 来切换武器和装备。当前 `XMNova.SC2Mod` 的 `UnitData.xml` 仍保留 `NovaEquipmentSwap` 引用和武器子菜单按钮，但 `XMNova.SC2Mod/Base.SC2Data/GameData/AbilData.xml` 里没有定义 `NovaEquipmentSwap`；这说明当前 mod 对装备切换可能依赖别的拼装模块、SC2 依赖链，或保留了官方结构但裁剪了局部定义。实现时不能只看按钮存在，必须验证 `AbilData -> EffectData -> BehaviorData -> WeaponData` 是否闭合。

### 技能和特性如何随形态变化

技能可用性主要靠 `Requirement` / `Validator`，不是靠 Galaxy 里手写大量 if/else。

例子：

```text
AbilData.xml
NovaCoopDecoyTarget.Execute -> Requirements=HaveNovaCombatSuit
NovaBlink.Execute           -> Requirements=HaveNovaCombatSuit
NovaWeaponHellfireShotgunBlast.Execute -> Requirements=HaveNovaCombatSuit

RequirementData.xml
HaveNovaCombatSuit -> CountBehaviorNovaCombatSuitCompleteOnlyAtUnit

RequirementNodeData.xml
CountBehaviorNovaCombatSuitCompleteOnlyAtUnit -> Count NovaCombatSuit at unit
```

潜行形态和突击形态的按钮可以占同一格命令卡，因为需求不同：

```text
UnitData.xml
NovaWeaponImprovedCanisterRifleSnipe -> Row=2 Column=0
NovaWeaponHellfireShotgunBlast       -> Row=2 Column=0

NovaGadgetBoombots -> Row=2 Column=2
NovaBlink          -> Row=2 Column=2

NovaArmorStealthSuit -> Row=2 Column=1
NovaArmorCombatSuit  -> Row=2 Column=1 Requirements=HaveNovaCombatSuit
```

因此按钮不是“运行时移动了位置”，而是多个按钮预先声明在同一个格子里，再由需求决定当前显示哪一个。这个模式非常适合做数据驱动 profile：profile 只声明“哪个 mode 下哪个 button/ability 可见”，运行时不直接手写按钮显隐。

### 伤害和特效如何随状态变化

武器数据也会继续分支。例如 `NovaWeaponImprovedCanisterRifle` 使用：

```text
WeaponData.xml
NovaWeaponImprovedCanisterRifle
  Effect = NovaWeaponImprovedCanisterRifleCloakedSwitch

EffectData.xml
NovaWeaponImprovedCanisterRifleCloakedSwitch
  CasterIsCloaked -> NovaWeaponImprovedCanisterRifleCloaked
  default         -> NovaWeaponImprovedCanisterRifleUncloaked
```

这意味着同一个武器也能根据“是否隐形”走不同伤害效果。形态切换不是只影响 UI；它会影响行为状态，而行为状态又被武器、效果、需求、actor 多处读取。

### Actor、模型、语音如何跟着变

`ActorData.xml` 监听 `NovaCombatSuit` 和武器 behavior：

```text
Behavior.NovaCombatSuit.On  -> SetWireframe shotgun
Behavior.NovaCombatSuit.Off -> SetWireframe terran-nova
Behavior.NovaCombatSuit.On  -> SetGroupIcon shotgun
Behavior.NovaCombatSuit.Off -> SetGroupIcon terran-nova
Behavior.NovaCombatSuit.On  -> AnimGroupApply B / Remove A
Behavior.NovaCombatSuit.Off -> AnimGroupApply A / Remove B

Abil.NovaKitSwap,On  -> NovaCommander_AssaultMode
Abil.NovaKitSwap,Off -> NovaCommander_StealthMode
```

所以如果以后做控制反转，不能只在初始化里给单位加行为。至少要校验：

1. mode behavior 存在。
2. button / abil / command 存在。
3. requirement / validator 能根据 behavior 正确切换按钮。
4. weapon / effect 闭合。
5. actor 对 behavior 和 weapon 的事件绑定存在。
6. 语音 sound 绑定存在，否则点击有切换但没有语音。

### 与官方合作指挥官的关系

官方合作指挥官数据里，诺娃 3 级解锁 `NovaKitSwap`：

```text
游戏数据/官方合作指挥官/commanders/Nova/progression.json
level=3
ability_commands:
  NovaKitSwap,cmd=1
  NovaKitSwap,cmd=""
```

15 级 `NovaStanceDance` 会改切换：

```text

  NovaKitSwap On/Off 冷却 -15
  NovaStealthSuitInitialSet Chance = 1
  NovaCombatSuitInitialSet Chance = 1
```

当前 mod 里也保留了同样方向：

```text
UpgradeData.xml
NovaStanceDance
  Abil,NovaKitSwap,Cost[0].Cooldown.TimeUse -15
  Abil,NovaKitSwap,OffCost[0].Cooldown.TimeUse -15
  Effect,NovaStealthSuitInitialSet,Chance = 1
  Effect,NovaCombatSuitInitialSet,Chance = 1
```

差异点是：官方 `starcoop` 的 `NovaEquipmentSwap` 装备切换闭包是完整的；当前 `XMNova` 中形态切换闭包比较清楚，装备切换闭包需要跨依赖继续验证，不能直接默认已经完整。

### 测试闭包

Nova 的静态校验至少要覆盖：

1. `NovaCoop` 是否有 `NovaKitSwap`、`NovaPermanentlyCloaked`、初始武器。
2. `NovaKitSwap` 是否是 toggle `CAbilBehavior`，是否指向 `NovaCombatSuit`。
3. `NovaCombatSuit` 是否禁用潜行行为、切换武器、触发进入/离开效果。
4. `HaveNovaCombatSuit` 是否能追到 `CountBehaviorNovaCombatSuitCompleteOnlyAtUnit`。
5. 同格按钮是否都有需求约束，避免两个形态按钮同时显示。
6. `ActorData` 是否有 `Behavior.NovaCombatSuit.On/Off` 对应的 wireframe、group icon、动画组和语音。
7. 如果启用装备切换，`NovaEquipmentSwap` 是否能追到 `Specialize -> EffectSet -> RemoveBehavior -> ApplyBehavior -> Weapon`。
8. `NovaStanceDance` 是否实际修改 `NovaKitSwap` 冷却和两个切换效果的 `Chance`。

这类测试不需要一开始就做成大型解析器。最小闭环可以先为 Nova 写一条专用静态检查，把上述 id 串起来；等 Nova 通过后，再抽象成通用 `CommanderHeroModeProfile` / `CommanderHeroLoadoutProfile` 校验器。

## 指挥官面板与顶部技能条接入

面板不是英雄单位命令卡。英雄技能按钮通常在英雄 `UnitData.CardLayouts` 上；指挥官顶部技能条通常是独立的 caster 单位、Dialog 面板和 caster unit group 共同实现。

当前 `合作指挥官版起义狂潮` 里已经有一条通用面板链路：


### 面板闭包

```text

  -> AbilData / CmdButtonArray
  -> ButtonData
  -> RequirementData
  -> EffectData
```

这里最容易漏的不是模型，而是：

5. 技能需要 charge/energy/cooldown，面板没有刷新。
6. 技能效果依赖全局触发器，例如诺娃空投、斯台特曼卫星、泰凯斯招募计时。

### 面板和英雄技能的边界

不要把这两类混在一起：

| 类型 | 入口 | 例子 | 主要 owner |
|---|---|---|---|
| 英雄命令卡技能 | 英雄 `UnitData.CardLayouts` | 德哈卡吞噬、跳跃猛击 | 英雄单位 Catalog |
| 指挥官顶部技能 | `CoopCaster/SoACaster/Caster*` + Dialog | 雷诺空投、亚顿之矛、德哈卡原始族群、诺娃空投 | 面板 caster + XMCore/XMFinal runtime |
| 运行时特殊机制 | Galaxy hook + Catalog | 泰凯斯招募计时、斯台特曼卫星、斯旺激光钻机 | 指挥官专用 runtime |

判断一个技能应该接哪一层：

1. 选中英雄后出现在命令卡上，归 `CommanderHeroAbilityProfile`。
2. 不选中英雄也在屏幕顶部/侧边出现，归 `CommanderPanelAbilityProfile`。
3. 技能本体是 Catalog，但按钮、冷却、充能或目标转发靠 Dialog/trigger，必须同时登记面板 profile 和 runtime profile。
4. 如果技能依赖 `BankValueGetAsInt` 的精通、威望或等级位，要在 profile 标出 `MasteryModifier` / `PrestigeModifier`，并在日志里输出最终值。

### 面板控制反转落地方式

面板可以走和地图初始化、科技链相同的控制反转思路，但反转点不是 Dialog 控件本身。SC2 的 Dialog 按钮没有面向对象接口，也不适合让每个按钮自己承载复杂逻辑。正确反转点是：

```text
CommanderPanelProfile
  -> 声明这个指挥官用哪个 caster、哪个模板、几个按钮、哪些状态刷新
CommanderPanelAbilityProfile
  -> 声明每个面板按钮绑定哪个 caster ability、command、需求、冷却/充能
CommanderPanelRuntimeProfile
  -> 声明特殊运行时 hook，例如目标转发、能量刷新、召唤计时、卫星状态
XMFinal / XMCore dispatcher
  -> 只读取 profile 并调用统一初始化，不再写大段 commander if/else
```

也就是从：

```text
if commander == Raynor:
    create CoopCasterRaynor
    init Raynor panel
elif commander == Dehaka:
    create CasterDehaka
    init Dehaka panel
elif commander == Swann:
    create CasterSwann
    init Swann panel
...
```

收敛为：

```text
profile = CommanderPanelProfile[commander]
caster = CreateUnit(profile.CasterUnit)
CU_GPInit(player, profile.PanelKind, caster, profile.SecondaryCasterUnit)
BindCommandPanel(profile)
RunPanelInitHook(profile.RuntimeHook)
Log PANEL_INIT / PANEL_BIND / PANEL_STATE
```

### 面板 IoC 的边界

能数据化的内容：

1. caster 单位 id。
2. 面板类型和 Dialog 模板。
3. 按钮数量、按钮索引、按钮显示/隐藏条件。
4. 面板按钮绑定的 ability command。
5. 需求、升级、精通、威望修正。
6. 是否需要能量、充能、冷却刷新。
7. 是否需要目标点选转发。
8. 初始化、显示隐藏、状态刷新 hook 名称。

不建议数据化的内容：

1. `DialogControlCreateInPanelFromTemplate` 这类底层控件创建细节。
2. `UISetTargetingOrder` 的底层调用本身。
3. 泰凯斯招募计时、斯台特曼卫星、斯旺激光钻机这类有持续状态机的实现细节。
4. 复杂技能效果的伤害、搜索、buff、Actor 表现。

这些内容应该保留在共享 runtime 或 Catalog 中，由 profile 指向它们。

### 面板 dispatcher 建议

新增统一入口：

```text
XMPanel_InitForCommander(player, commander, secondUnit)
```

职责：

1. 读取 `CommanderPanelProfile`。
2. 创建 caster 单位。
3. 创建或复用 caster group。
4. 调用统一 `CU_GPInit` 或 profile 指定的 `InitFunction`。
5. 绑定 command panel 到 caster group。
6. 执行 `CommanderPanelRuntimeProfile.InitHook`。
7. 输出 `[XM_DBG][PANEL_INIT]`。

新增统一刷新入口：

```text
XMPanel_UpdateState(player, commander, reason)
```

职责：

1. 刷新能量、充能、冷却。
2. 刷新按钮禁用/解锁状态。
3. 刷新精通/威望影响后的最终数值。
4. 输出 `[XM_DBG][PANEL_STATE]`。

新增统一目标转发入口：

```text
XMPanel_ForwardTargetingOrder(player, ability, targetPoint)
```

职责：

1. 根据 `CommanderPanelAbilityProfile.TargetingMode` 判断是否需要目标点。
2. 找到 caster group。
3. 调用 `UISetTargetingOrder`。
4. 输出 `[XM_DBG][PANEL_TARGETING]`。

### 面板 IoC 迁移顺序

建议不要一次性改所有指挥官。先选三类代表：

| 类型 | 指挥官 | 原因 |
|---|---|---|
| 通用 caster 面板 | 雷诺 | 按钮少，适合验证通用初始化 |
| 英雄 + 面板并存 | 德哈卡 | 可验证英雄技能和面板技能边界 |
| 特殊状态面板 | 斯旺或斯台特曼 | 可验证 caster group、能量/状态刷新和专用 hook |

迁移标准：

1. 旧 `if/else` 仍保留 fallback。
2. profile dispatcher 先只服务试点指挥官。
3. 静态脚本确认 caster、ability、button、template、hook 都存在。
4. 运行时日志能看到 `PANEL_INIT`、`PANEL_BIND`、`PANEL_STATE`。
5. 试点通过后再把更多指挥官迁进 profile。

### 面板一致性流程

1. 从官方 CASC 导出每个指挥官的 caster 单位、面板技能和本地化。
2. 从 `原始mod` 抽取已经拼过的 caster、Dialog、触发器和技能链。
3. 从当前 `XMFinal`/`XMCore` 抽取实际会创建的 caster 和实际调用的 `CU_GPInit*`。
4. 比对三层差异：官方应该有什么、原始mod 拼了什么、当前 runtime 实际接了什么。
5. 对缺失项分类：缺 caster、缺面板模板、缺按钮、缺技能、缺目标转发、缺计时/能量刷新、缺专用 hook。

建议脚本：

```text
scripts/sc2/export-commander-panel-closure.ps1
scripts/sc2/compare-commander-panel-closure.ps1
scripts/sc2/validate-commander-panel-profiles.ps1
```

## 分阶段实施计划

### 阶段 0：盘点与保护

目标：先建立可回归基线，不急着大改。

工作项：

1. 固定当前 `XMFinal`、关键地图、科技建筑 XML 的索引。
2. 导出当前地图内 commander 分支清单。
3. 导出当前科技建筑按钮/研究项/升级项清单。
4. 选定一个指挥官和一个科技链作为试点。

建议试点：

- 地图初始化：阿巴瑟或凯瑞甘。

## 日志与诊断方案

控制反转以后，问题定位不能只靠“地图里搜 if/else”。需要在统一入口增加可被 AI 解析的日志。

日志目标：

1. 让 AI 能判断当前地图实际读到哪个 commander。
2. 让 AI 能判断进入了哪个 `ScenarioKind`。
3. 让 AI 能判断命中了哪个 profile、是否 fallback。
4. 让 AI 能判断实际创建了哪些单位、数量、玩家、位置。
5. 让 AI 能判断科技 profile 生成了哪些按钮、需求、升级项。
6. 让 AI 能快速发现缺失对象、空 profile、错误 commander、错误 building。

### 双通道日志

建议同时保留两个通道。

#### 1. GameLogs 文本通道

使用 SC2 原生 `TriggerDebugOutput` 输出结构化文本，写入 `Documents/StarCraft II/GameLogs`。

格式统一为：

```text
[XM_DBG][LEVEL][PHASE] key=value key=value key=value
```

示例：

```text
[XM_DBG][INFO][INIT_START] player=1 map=traynor01 commander=Abathur scenario=standard_base
[XM_DBG][INFO][PROFILE_HIT] type=CommanderRuntimeProfile commander=Abathur profile=AbathurRuntime
[XM_DBG][WARN][PROFILE_FALLBACK] commander=Abathur scenario=no_base_ultimate fallback=no_base_heavy reason=missing_requirement
[XM_DBG][ERROR][MISSING_UNIT] commander=Abathur scenario=cargo_heavy unit=RavagerAbathurReborn source=CommanderScenarioLoadout
```

优点：

- 不需要额外 Bank 文件。
- 方便 AI 用 `Select-String` / `rg` 直接搜索。
- 适合记录过程型事件。

要求：

- 必须使用固定前缀 `[XM_DBG]`。
- 字段使用 `key=value`，不要写自然语言长句。
- value 不使用空格；需要空格时改成 `_` 或短 ID。
- 每条日志包含 `player`、`commander`、`map` 或能从上下文推导的 trace id。

#### 2. Debug Bank 结构化快照通道

使用独立调试 Bank 保存最终状态快照，建议名称：

```text
XMDebug.SC2Bank
```

建议 Section：

```text
Run
Commander
Scenario_<kind>
Profile_<profileId>
Unit_<unitId>
Tech_<upgradeId>
Error_<index>
```

建议字段：

```text
Run:
  Map
  Commander
  Player
  DebugEnabled
  LastPhase
  ErrorCount

Scenario_<kind>:
  Entered
  ProfileFound
  Fallback
  UnitCount
  LastError

Unit_<unitId>:
  Requested
  Created
  Owner
  ScenarioKind
  ApplyFullBiomass

Tech_<upgradeId>:
  Unit
  Building
  Button
  Requirement
  Upgrade
  Validated
```

优点：

- 适合 AI 脚本解析成 JSON。
- 适合跨地图保留最后一次运行状态。
- 适合对比“预期 profile”和“实际创建结果”。

要求：

- Debug Bank 和正式进度 Bank 分离，避免污染玩家进度。
- 默认只在 debug 开关开启时写入。
- 每次地图开始时写入 `Run`，每个关键阶段更新 `LastPhase`。

### Debug 开关

建议三种入口：

1. Launcher 写入 Bank：

```text
Settings.DebugMode = 1
Settings.DebugLevel = info|warn|error|trace
```

2. 游戏内聊天命令：

```text
-xmdebug on
-xmdebug off
-xmdebug trace
```

3. 开发期硬编码临时开关：

只允许在试点阶段短期使用，最终必须回到 Bank / chat command。

### 日志级别

```text
ERROR: 缺对象、profile 为空、创建失败、关键 hook 失败。
WARN: 使用 fallback、跳过可选单位、需求未满足。
INFO: 初始化开始/结束、profile 命中、单位创建汇总。
TRACE: 每个字段读取、每个单位逐条创建、每个按钮生成。
```

默认建议：

- 实机普通测试：`INFO`
- AI 排查问题：`TRACE`
- 玩家发布版：关闭，或只保留 `ERROR`

### 必须打点的位置

地图初始化链路：

1. 读取 Bank 后：

```text
[XM_DBG][INFO][BANK_READ] player=1 commander=Abathur map=traynor01
```

2. 进入场景 helper：

```text
[XM_DBG][INFO][SCENARIO_ENTER] scenario=no_base_heavy commander=Abathur
```

3. 查 profile：

```text
[XM_DBG][INFO][PROFILE_HIT] type=CommanderScenarioLoadout commander=Abathur scenario=no_base_heavy rows=3
```

4. fallback：

```text
[XM_DBG][WARN][PROFILE_FALLBACK] scenario=no_base_ultimate fallback=no_base_heavy reason=ultimate_locked
```

5. 创建单位：

```text
[XM_DBG][INFO][UNIT_CREATE] unit=RoachVile count=2 player=1 scenario=no_base_heavy result=ok
```

6. hook：

```text
[XM_DBG][INFO][HOOK_RUN] commander=Abathur hook=PostInit result=ok
```

7. 初始化结束：

```text
[XM_DBG][INFO][INIT_DONE] commander=Abathur scenario=standard_base errors=0 warnings=1
```

科技链路：

1. 读取 `CommanderUnitTechProfile`：

```text
[XM_DBG][INFO][TECH_PROFILE] commander=Abathur unit=Hydralisk building=EvolutionChamber
```

2. 生成/验证按钮：

```text

```

3. 生成/验证升级：

```text
[XM_DBG][INFO][TECH_UPGRADE] unit=Hydralisk upgrade=GroovedSpines requirement=HasHydraliskDen result=ok
```

4. 缺口：

```text
[XM_DBG][ERROR][TECH_MISSING] unit=Hydralisk field=Button id=ResearchGroovedSpines
```

### AI 排查流程

后续 AI 定位问题时优先按这个顺序：

1. 运行 `parse-latest-xm-debug-log.ps1 -AsJson`。
2. 如果没有日志，确认 `Settings.DebugMode` 或 `-xmdebug on`。
3. 看 `Errors`，先处理缺对象、空 profile、创建失败。
4. 看 `Warnings`，确认 fallback 是否符合预期。
5. 看 `Scenario`，确认地图传入的场景语义是否正确。
6. 看 `Units`，确认实际创建和 profile 是否一致。
7. 看 `Tech`，确认按钮、需求、升级项是否闭环。
8. 再回到 XML/Galaxy 查具体定义。

不要先全仓搜索字符串。日志里有 trace id 和 phase 时，优先从日志链路反推。

#### 场景类型

测试台至少覆盖这些 `scenarioKind`：

| 场景 | 目的 |
|---|---|
| `standard_base` | 验证基地、工人、第二建筑、caster、英雄、面板 |
| `no_base_light` | 验证无基地轻型开局小队 |
| `no_base_heavy` | 验证无基地重型/英雄小队 |
| `cargo_light` | 验证运输机货舱轻型单位 |
| `cargo_heavy` | 验证运输机货舱重型单位 |
| `cargo_air` | 验证运输机或支援空军单位 |
| `bonus_reward` | 验证奖励/救援/额外单位生成 |
| `full_buildings` | 生成该指挥官所有可用建筑 |
| `full_units` | 生成该指挥官所有核心兵种、英雄、特殊单位 |
| `initial_units` | 生成官方基础状态审计清单，只用于对照和排错 |
| `level15_units` | 生成当前默认 15 级全解锁后的满级兵种清单 |
| `fusion_final_units` | 生成 15 级 + 精通全满 + 威望正面融合后的最终兵种清单 |
| `hero_modes` | 验证诺娃形态、德哈卡等级、泰凯斯小队等英雄状态 |
| `panel_smoke` | 验证 caster、面板、顶部技能按钮和目标转发 |
| `tech_smoke` | 验证攻防和专属科技至少可见、可研究、可影响对象 |

`full_units` 不是实战平衡测试。它的目标是“对象能创建、模型能显示、Actor 不炸、能力按钮不缺、核心行为能挂上”。单位可以按格子生成，关闭 AI，给足资源和补给。

注意：当前 commander 默认就是 15 级，不从 1 级开始。后续默认的 `full_units` 应按强度融合后的最终状态理解，等价于 `fusion_final_units`。如果要排查官方基础链路，再显式跑 `initial_units`。满级之后兵种本身可能变化，例如新增可训练单位、低级单位被高级变体替代、终极进化加入清单、英雄形态改变攻击方式或行为。

#### 地图布局

建议使用一张空白测试地图，划分固定区域：

```text
BaseZone      基地和工人
CargoZone     运输机和货舱落点
SquadZone     无基地开局小队
RosterZone    全单位/全建筑展示
HeroZone      英雄形态、演化、技能测试
EnemyZone     敌方目标、装甲类型、空地目标
PanelZone     面板技能目标点
LogZone       文本标签或测试摘要区域
```

所有测试生成的单位都加入测试专用 unit group。切换 commander 或场景前先清理这个 group，避免上一轮单位污染下一轮。

#### 数据来源

测试台的数据不要手写在地图里到处散落。优先顺序：

1. `CommanderScenarioLoadout`：基地、无基地、运输机、奖励、支援单位。
2. `CommanderHeroProfile` / `CommanderHeroModeProfile`：英雄、形态、专属状态。
3. `CommanderPanelProfile`：caster、面板、顶部技能。
4. `CommanderUnitTechProfile`：科技建筑、攻防、专属科技。
5. `CommanderRosterProfile`：全建筑、全单位、特殊单位展示清单；必须区分初始、15 级和强度融合最终清单。
6. `CommanderLevelUnlockProfile`：提供满级解锁对 roster 的新增、替换和变体关系。

如果某个指挥官还没有 profile，可以先有临时 fallback，但必须打日志：

```text
[XM_DBG][WARN][TEST_PROFILE_FALLBACK] commander=Swann profile=CommanderRosterProfile reason=missing fallback=legacy-helper
```

#### 控制反转关系

测试台本身不应该知道“凯瑞甘要生成什么单位、诺娃要怎么切形态”。它只发起测试请求：

```text
TestBench UI
  -> scenarioKind
  -> XMFinal dispatcher
  -> commander profile / commander hook
  -> 创建单位、建筑、caster、英雄、面板
```

这样它既是测试工具，也是控制反转架构的验收入口。如果测试台必须写大量 commander if/else，说明 runtime dispatcher 还没有抽出来。

#### 自动跑全量

在手动按钮之外，建议加 `Run All Smoke`：

```text
for commander in commanders:
  for scenario in smokeScenarios:
    clear
    run
    wait 0.5-1.0s
    summarize
```

全量模式不需要玩家逐个点，但仍要保留手动模式。手动模式用于观察模型、技能面板、诺娃形态切换、德哈卡吞噬、泰凯斯招募等视觉或交互项。

#### 边界和风险

同一局连续切换有明显价值，但不能把它当成完全干净的新局验证。

主要风险：

1. `TechTreeUpgradeAddLevel` 通常是累加状态，切换 commander 后不一定能完全回滚。
2. `Bank`、全局变量、触发器、计时器、caster group、Dialog 控件可能残留。
3. `XMFinal.Initialize` / `InitializeBase` 当前不是为多次调用设计的，直接重复调用可能泄露面板或重复注册触发器。
4. 某些 commander 机制依赖地图专有区域、目标、敌人或任务触发器，测试台只能验证闭包，不能验证完整任务语义。
5. 面板和 top-bar 如果无法安全销毁重建，第一阶段可以只验证 caster 和按钮闭包；完整交互再做单 commander 新局测试。

因此测试台分两类结论：

| 结论类型 | 可以由测试台直接判断 | 仍需真实地图确认 |
|---|---|---|
| 对象存在 | 单位、建筑、按钮、Ability、Effect、Actor 是否缺失 | 否 |
| 生成闭包 | 基地、货舱、小队、全 roster 能否生成 | 部分 |
| 满级兵种变化 | `initial_units`、`level15_units`、`fusion_final_units` 的新增/替换关系是否符合 profile | 真实战斗表现仍需确认 |
| 面板闭包 | caster、按钮、目标转发是否基本存在 | 复杂状态仍需确认 |
| 状态/升级 | 能否加升级、能否显示科技 | 升级回滚和真实流程需要新局 |
| 任务语义 | 不适合完全判断 | 必须真实地图 |

#### 推荐实施顺序

第一阶段只做最小闭环：

1. 复制或新建一张空白 `CommanderTestBench.SC2Map`。
2. 地图依赖 `XMFinal.SC2Mod`。
3. 地图 UI 只做 commander 列表、清理、标准基地、运输机、全单位。
4. `XMFinal` 暴露或复用一个 test dispatcher。
5. 先接 3 个指挥官：Raynor、Nova、Abathur。
6. 输出 `[XM_DBG][TEST_*]` 日志。
7. 手动启动一次游戏，连续点 3 个指挥官完成验证。

第二阶段扩展：

1. 接入全部 18/19 个指挥官。
2. 增加 `Run All Smoke`。
3. 增加 `full_buildings`、`initial_units`、`level15_units`、`fusion_final_units`、`hero_modes`。
4. 增加日志解析脚本，自动汇总每个 commander/scenario 的 error。

第三阶段用于架构验收：

1. 所有测试场景都从 profile 读取。
2. 测试台不再有 commander-specific if/else。
3. 新 commander 接入时，先能在测试台通过，再进真实战役地图。
4. 真实地图只验证任务语义，不再承担基础闭包排错。

## 风险与约束

1. Galaxy 没有真正接口和动态函数调用，不能照搬传统 IoC 容器。
2. 过度运行时动态化会增加地图加载风险和调试难度。
3. Command Card、Research Ability、Requirement 更适合静态生成，不适合运行时拼。
4. 一次性全量迁移风险高，应先做试点。
5. 旧地图里已有任务特殊逻辑，不应为了抽象强行抹平。
6. 特殊 commander 机制保留 hook，但 hook 必须集中在 `XMFinal` 或公共库。
7. 日志不能默认刷屏；发布版默认关闭，开发版通过 Bank 或聊天命令开启。
8. Debug Bank 必须和正式进度 Bank 分离，避免污染玩家数据。

## 推荐先做的最小闭环

第一轮只做两个闭环。

### 闭环 0：雷诺强度融合试点

在做通用化之前，先用雷诺验证一套“等级满级、精通全满、威望只取优点”的融合模型。设计文档见：

```text
docs/指挥官威望/雷诺精通威望加点融合设计-2026-05-27.md
```

这个试点的关键点是不要直接启用官方三个 `PlayerPrestige`，而是把正面效果拆出来独立应用；精通点不依赖玩家 Bank，而由融合 profile 明确把 6 项 `MasteryRaynor*` 都加到 30 级。

### 闭环 A：地图初始化

范围：

- 1 个指挥官。
- 1 张标准基地图。
- 1 张无基地图或运输图。

交付：

- `CommanderRuntimeProfile`
- `CommanderScenarioLoadout`
- `XMFinal` 统一 helper
- 对应地图改为传 `ScenarioKind`
- `[XM_DBG]` 日志和 Debug Bank 快照
- 静态和游戏内冒烟验证

### 闭环 B：科技链

范围：

- 1 个指挥官。
- 1 个兵种。
- 1 个攻防升级组。
- 1 个专属科技。

交付：

- `CommanderUnitTechProfile`
- 审计脚本
- 生成 patch 或手工等价 patch
- `validate-*-tech-chain.ps1` 增强
- 科技 profile 生成/验证日志
- 游戏内研究验证

### 闭环 C：单位演化与能力

范围：

- 1 个指挥官。
- 1 个基础单位。
- 1 条演化链。
- 1 个主动技能。
- 1 个被动或属性增强。

交付：

- `CommanderUnitEvolutionProfile`
- `CommanderUnitAbilityProfile`
- `CommanderUnitStatProfile`
- `CommanderRosterProfile` 的满级/最终兵种清单
- 演化链验证脚本
- 能力链验证脚本
- `[XM_DBG]` 演化与能力日志
- 游戏内演化、释放技能、升级后属性验证

## 最终完成标准

不要把“写了 profile”当成完成。完成应满足：

1. 试点地图里不再新增 commander if/else。
2. 试点科技建筑里不再新增兵种规则硬编码。
3. Profile 能被脚本验证。
4. XML 生成或 patch 能复跑。
5. 游戏内至少完成一轮 Launcher -> 地图 -> 初始化 -> 科技研究闭环。
6. 试点单位至少完成一轮训练/创建 -> 技能释放 -> 科技升级 -> 演化/变体切换闭环。
7. 文档更新到新接入流程。
