# 指挥官测试台与回归验证设计

日期：2026-05-27

## 目标

后续不能靠“进一张地图，发现一个指挥官坏了，再改一处 if/else”来验证合作指挥官。测试体系要同时解决两个问题：

1. 在进入游戏前，用脚本尽早发现数据闭包缺口。
2. 在游戏内，用一张专用测试地图一次启动后切换 18 个指挥官，验证初始化、强度融合、英雄、普通单位、建筑、科技、运输机和特殊机制。

测试台不是正式战役地图，也不是平衡测试地图。它的职责是把对象缺失、按钮断链、初始化失败、面板未接入、满级 roster 变化错误这类问题提前暴露出来。

## 基本口径

1. 指挥官默认 15 级。
2. 六项精通默认全部 30 点。
3. 威望只取正面收益，不直接启用官方 `PlayerPrestige`。
4. `full_units` 默认等价于 `power_fusion` / `fusion_final_units`。
5. `initial_units` 只用于官方基础状态审计和差异对照。
6. `XMFinal.SC2Mod` 是运行时 owner；测试地图只发起测试请求，不承载指挥官规则。
7. `合作指挥官版起义狂潮/` 是当前开发 owner；`原始mod/` 是拿原 mod 续上的新项目，用于测试新写法和回归。测试设计仍以 `XMFinal.SC2Mod` 统一 runtime owner 为准，不能把任一工程线当作官方权威来源。

## 总体分层

```text
静态数据验证
  -> 生成测试 Profile / 缺口报告
  -> CommanderTestBench.SC2Map 游戏内冒烟
  -> [XM_DBG] 日志与 Debug Bank
  -> 真实战役地图回归
```

每一层的结论不同：

| 层级 | 能确认 | 不能确认 |
|---|---|---|
| 静态数据验证 | JSON/Profile 引用对象是否存在，Ability/Button/Requirement/Upgrade 是否可追踪 | 游戏内效果是否真的生效 |
| 测试台 | 单位能否创建，模型/Actor 是否炸，按钮是否出现，初始化器是否可重复调用 | 正式任务语义、剧情触发器、长期升级回滚 |
| 日志/Bank | 哪个 commander、scenario、phase 失败，失败字段是什么 | 视觉表现和手感 |
| 真实地图回归 | 场景语义、任务目标、运输机、奖励、剧情是否符合预期 | 全量 18 指挥官快速覆盖 |

## 静态验证设计

静态验证优先从当前数据源生成清单：

```text
游戏数据/官方合作指挥官/commanders/<Commander>/
docs/newdocs/指挥官细化/<Commander>.md
references/sc2-build-96883-casc-export/
crys_the_swarm_reborn.SC2Mod/Base.SC2Data/GameData/
```

第一阶段建议增加这些脚本：

```text
scripts/sc2/validate-commander-json-coverage.ps1
scripts/sc2/validate-commander-roster-closure.ps1
scripts/sc2/validate-commander-ability-closure.ps1
scripts/sc2/validate-commander-tech-closure.ps1
scripts/sc2/export-testbench-roster.ps1
```

静态检查项：

| 检查项 | 说明 |
|---|---|
| Commander 覆盖 | 18 个 commander 都有 `commander.json`、`roster.json`、`units.json`、`buildings.json`、`command_cards.json` |
| Roster 阶段 | 每个 commander 至少能区分 `initial`、`level15`、`power_fusion` |
| Unit/Building 存在 | `units.json`、`buildings.json`、`roster.json` 引用对象能在当前 Mod 或官方导出中找到 |
| 英雄候选 | `heroes.json=0` 时不直接判失败，而是标记 `needs-casc-or-runtime-audit` |
| Ability 闭包 | Unit -> Ability -> Command -> Button -> Requirement -> Effect/Behavior/Validator |
| 科技闭包 | ResearchBuilding -> ResearchAbility -> Button -> Upgrade -> Requirement -> AffectedObject |
| 演化闭包 | SourceUnit -> Ability -> Requirement -> Morph/Cocoon -> TargetUnit |
| 文本闭包 | Button/Tooltip/GameStrings 不缺 key |

输出结果建议写到：

```text
tmp/sc2-testbench-static/<yyyyMMdd-HHmmss>/
```

输出文件：

```text
coverage.json
missing-objects.md
missing-abilities.md
missing-tech.md
testbench-roster.json
```

## 单图测试台设计

建议新增一张专用测试地图：

```text
CommanderTestBench.SC2Map
```

测试地图可以放在后续确定的测试资产目录中，但它不应把 `合作指挥官版起义狂潮/` 当作权威来源。运行时依赖应指向 `原始mod/` 当前统一 runtime：

```text
XMFinal.SC2Mod
```

测试台只做四件事：

1. 显示指挥官与测试场景按钮。
2. 调用 `XMFinal` 的统一测试入口。
3. 清理和重跑当前测试状态。
4. 展示摘要并输出 `[XM_DBG]` 日志。

测试台不做：

1. 不在地图里维护各指挥官单位清单。
2. 不在地图里写大量 commander if/else。
3. 不直接拼技能、科技和威望逻辑。
4. 不替代正式战役地图验证。


如果某个入口内部仍需要 commander 分发，分发只能集中在 `XMFinal` 或指挥官 runtime hook 中，不能散落到测试地图。

第一版测试台至少覆盖：

| 场景 | 目的 |
|---|---|
| `standard_base` | 基地、工人、基础生产建筑、caster、顶部面板 |
| `power_fusion` | 15 级、六精通全满、威望正面融合 |
| `full_buildings` | 生成该指挥官最终建筑清单 |
| `full_units` | 生成 `power_fusion` 最终兵种清单 |

| `level15_units` | 生成 15 级解锁后的清单 |
| `fusion_final_units` | 生成融合最终清单，默认等同 `full_units` |
| `hero_modes` | 英雄、形态、战甲、亡命徒、召唤首领等 |
| `unit_ability_smoke` | 普通单位主动技能、被动行为、武器链 |
| `unit_evolution_smoke` | 阿巴瑟终极进化、单位变体、形态切换 |
| `panel_cost_smoke` | 顶部面板扣费、充能、冷却、资源变化 |
| `panel_effect_smoke` | 顶部面板指向性目标和实际效果 |
| `tech_smoke` | 攻防、专属科技、研究按钮和 Requirement |
| `cargo_light` | 运输机轻型空投单位 |

| `personal_smoke` | 雷诺矿骡/星轨、斯旺灭火、凯拉克斯自动维修等 |

`Run All Smoke` 的目标矩阵：

```text
for commander in 18 commanders:
  SetCommander
  Clear
  Run power_fusion
  Run standard_base
  Run full_buildings
  Run full_units
  Run hero_modes
  Run unit_ability_smoke
  Run panel_cost_smoke
  Run tech_smoke
  Run special_smoke
  Summarize
```

当前地图按钮 `Run Smoke` 先只跑当前 commander 的最小集合：

```text
power_fusion
standard_base
panel_cost_smoke
full_buildings
full_units
```

每个场景前先 `Clear`，每个场景后记录一次 `TEST_RUN_ALL_STEP`，最后用 warnings/errors 聚合出 `TEST_RUN_ALL_DONE result=ok|warning|error`。不能无条件输出 `result=ok`，因为 Raynor 面板现在仍是 `metadata_only` warning。

测试地图应划固定区域，避免单位互相干扰：

| 区域 | 用途 |
|---|---|
| `BaseZone` | 基地、工人、开局建筑 |
| `RosterZone` | 全单位和全建筑展示 |

| `TechZone` | 科技建筑、研究目标、升级验证单位 |
| `CargoZone` | 运输机、货舱、空投落点 |
| `PanelZone` | 顶部技能目标点 |

## 顶部面板测试

顶部面板要作为独立测试维度，不只在 `standard_base` 里确认 caster 存在。大多数顶部技能是指向性的，测试顺序固定为：

```text
InitPanel
  -> SnapshotCostState
  -> InvokePanelAbility
  -> VerifyCostOrCharge
  -> VerifyEffect
  -> WriteSummary
```

### panel_cost_smoke

先验证扣费和状态变化，不先讨论伤害或召唤效果。

检查项：

| 项 | 说明 |
|---|---|
| 可见性 | 面板按钮存在，等级/精通/威望融合后应可用 |
| 可用性 | Requirement 满足，按钮不是错误禁用 |
| 资源扣费 | 矿物、瓦斯、自定义资源或能量是否按预期变化 |
| 充能扣减 | charges 是否减少，最大充能是否正确 |
| 冷却启动 | cooldown 是否从 0 进入预期冷却 |
| 精通/威望修正 | 冷却、充能速度、费用减免是否使用融合最终值 |

日志：

```text
[XM_DBG][INFO][PANEL_COST_BEFORE] commander=Raynor ability=Hyperion minerals=100000 gas=100000 energy=200 charges=1 cooldown=0
[XM_DBG][INFO][PANEL_COST_AFTER] commander=Raynor ability=Hyperion minerals=100000 gas=100000 energy=200 charges=0 cooldown=240 result=ok
[XM_DBG][ERROR][PANEL_COST_MISMATCH] commander=Karax ability=OrbitalStrike field=energy expectedDelta=-5 actualDelta=0
```

### panel_effect_smoke

扣费确认后再验证效果。效果测试按技能类型分组，不强行用同一种断言覆盖所有面板技能。

| 技能类型 | 目标 | 效果断言 |
|---|---|---|
| 点目标伤害 | `XM_TB_PanelPoint` 附近敌方单位 | 目标生命下降、伤害 effect 命中、Actor 不报错 |
| 单位目标 | `XM_TB_EnemyGroundLight` / `XM_TB_EnemyGroundArmored` | 指定单位受到效果或行为 |
| 区域控制 | `XM_TB_EnemyZone` | 范围内单位获得 stun、slow、reveal 等行为 |
| 召唤/空投 | `XM_TB_PanelPoint` | 生成预期单位，归属正确，持续时间或计时器存在 |
| 全局技能 | 全地图或玩家状态 | 记录全局状态变化，必要时只做手动验证 |
| 特殊 runtime hook | commander hook | hook 被调用，输出专用日志 |

日志：

```text
[XM_DBG][INFO][PANEL_EFFECT_START] commander=Nova ability=Nuke target=XM_TB_PanelPoint mode=Point
[XM_DBG][INFO][PANEL_EFFECT_HIT] commander=Nova ability=Nuke target=EnemyGroundArmored beforeLife=1000 afterLife=250 result=ok
[XM_DBG][WARN][PANEL_EFFECT_MANUAL] commander=Vorazun ability=TimeStop reason=global-state-skill
```

第一阶段建议 `Run All Smoke` 只跑 `panel_cost_smoke`。`panel_effect_smoke` 先对 Raynor、Nova、Karax 这类目标明确的技能做白名单，等日志和清理稳定后再扩到全量。

触发策略：

| 测试目标 | 触发方式 |
|---|---|
| 扣费、充能、冷却、效果 | 命令触发，调用统一 `XM_InvokeCommanderPanelAbility` |
| 真实按钮接线 | 人工点击或单独 UI 接线测试 |

不要用模拟鼠标点击作为自动测试主路径。自动测试应直接给出 `panelAbilityId` 和目标点/目标单位；真实 UI 点击也必须解析到同一个 `panelAbilityId` 并调用同一个入口。这样既能稳定回归，又能防止测试逻辑和真实 UI 逻辑分叉。

## 同局切换的限制

单张测试地图一次启动切换所有指挥官很有价值，但不能把它当成完全干净的新局。

已知风险：

1. 玩家升级状态通常不能可靠回滚。
2. 全局变量、计时器、Dialog、caster group 可能残留。
3. 顶部面板可能无法安全销毁重建。
4. 某些机制依赖真实地图目标和任务触发器。
5. 多次调用初始化器可能暴露重复注册触发器、重复创建 caster、旧 group 未清理等问题。

当前测试台切换指挥官不再写真实 `CampaignXCore` Bank，而是启用 `XMRuntime` 的测试覆盖源。覆盖源只在运行时内存中设置当前 commander、`AchBit=255` 和六项精通 30 点；真实战役地图仍走原 Bank 读取路径。Debug Bank 后续只用于记录测试结果，不作为正式进度来源。

因此测试结论分级：

| 结论 | 测试台可判定 | 仍需真实地图新局确认 |
|---|---|---|
| Catalog 对象存在 | 是 | 否 |
| Profile 能读取 | 是 | 否 |
| 单位/建筑能创建 | 是 | 部分 |
| 满级 roster 是否包含最终对象 | 是 | 数值和平衡仍需确认 |

## 实施顺序

### 阶段 0：只做静态报告

目标：不用进游戏，先知道每个 commander 的数据缺口。

交付：

1. `export-testbench-roster.ps1`
2. `validate-commander-json-coverage.ps1`
3. `coverage.json`
4. `missing-objects.md`

验收：

1. 能列出 18 个 commander。
2. 能列出每个 commander 的 heroes、units、buildings、command cards、upgrades 数量。
3. `heroes.json=0` 的 commander 被标记为待补英雄闭包，而不是失败。

### 阶段 1：三指挥官测试台最小闭环

先接：

```text
Raynor
Nova
Abathur
```

原因：

| 指挥官 | 覆盖风险 |
|---|---|
| Raynor | 标准人族基地、星轨/矿骡、顶部面板、威望融合 |
| Nova | 英雄形态切换、精英单位、面板、形态攻击方式变化 |
| Abathur | 生物质、终极进化、非 heroes.json 英雄缺口、满级 roster 变化 |

交付：

1. `CommanderTestBench.SC2Map` 空白测试地图。
2. 指挥官列表 UI。
3. `SetCommander`、`Clear`、`standard_base`、`full_units`。
4. `[XM_DBG][TEST_*]` 日志。
5. 手动一次启动连续切换 3 个 commander。

验收：

1. 三个 commander 能切换。
2. 切换前能清理上一轮测试单位。
3. `full_units` 默认生成融合最终清单。
4. 缺对象能在日志中明确显示。

### 阶段 2：扩展到 18 指挥官

交付：

1. 18 个 commander 的 `standard_base`。
2. 18 个 commander 的 `full_buildings`。
3. 18 个 commander 的 `full_units`。
4. `Run All Smoke`。
5. 日志解析脚本输出总表。

验收：

1. 一次启动能跑完全量冒烟。
2. 每个 commander 都有 summary。
3. 每个失败都有 commander、scenario、object id。

### 阶段 3：能力、科技、演化闭包

交付：

1. `unit_ability_smoke`
2. `tech_smoke`
3. `unit_evolution_smoke`
4. `hero_modes`

重点试点：

| 指挥官 | 测试项 |
|---|---|
| Nova | 形态切换、攻击方式、形态特性、技能按钮 |
| Dehaka | 英雄等级、吞噬、精华、首领 |
| Tychus | 泰凯斯和 8 个亡命徒英雄、招募/装备 |
| Fenix | 战甲/英雄形态 |
| Zeratul | 英雄、神器碎片、面板技能 |
| Stetmann | 超级盖瑞、卫星、姿态 |
| Abathur | 终极进化、生物质保留 |

### 阶段 4：真实地图回归

测试台通过后，再选真实战役地图验证：

| 地图类型 | 验证内容 |
|---|---|
| 标准基地图 | 开局基地、工人、面板、第一波任务 |
| 无基地图 | 小队生成、英雄绑定、任务目标 |
| 运输机图 | 货舱单位、空投、控制权 |
| 奖励/支援图 | 奖励单位、空军支援、剧情触发 |

真实地图只验证场景语义，不再承担基础对象闭包排错。

## 成功标准

第一轮完成不以“有文档”作为标准，而以这些结果作为标准：

1. 有静态脚本能导出 18 指挥官测试清单和缺口。
2. 有测试地图能在同一局切换至少 Raynor、Nova、Abathur。
3. 测试地图不维护指挥官单位硬编码清单。
4. `XMFinal` 有统一测试入口。
5. 失败能通过 `[XM_DBG]` 定位到 commander、scenario、phase、object id。
6. `full_units` 默认验证 `power_fusion`，不是基础 `initial`。
7. 测试台结论和真实地图回归结论分开记录。
