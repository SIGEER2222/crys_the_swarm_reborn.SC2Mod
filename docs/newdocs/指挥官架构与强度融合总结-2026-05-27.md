# 指挥官架构与强度融合总结

日期：2026-05-27

## 总结结论

当前战役 mod 的合作指挥官架构，不能继续让地图、科技建筑、英雄技能和面板里到处写 commander if/else。后续应把指挥官能力拆成 profile 声明、Catalog 补丁、`XMFinal.SC2Mod` 运行时分发、测试台验证四类职责。

整理完精通、威望和兵种后，需要新增一个明确的“强度融合层”：默认 15 级全解锁、6 项精通全满、威望只取正面收益，并跳过官方为了平衡加入的负面代价。这个层不属于地图初始化，也不属于科技建筑研究逻辑。

当前玩法前提：指挥官运行时默认就是 15 级，不从 1 级开始。文档中的 `initial` 只用于官方基础状态审计、差异对照和测试台排错，不是默认战役玩法状态。

## 数据源优先级

当前有两条本地工程线：`原始mod/` 是拿原 mod 续上的新项目和当前实现/回归线；`合作指挥官版起义狂潮/` 是此前尚未成功的半成品旧测试实现，只能当实现线索，不能当设计依据或当前开发 owner。

优先级：

1. `游戏数据/官方合作指挥官/commanders/<Commander>/`
2. `references/sc2-build-96883-casc-export/`
3. `原始mod/`
4. `合作指挥官版起义狂潮/`

含义：

- `游戏数据/官方合作指挥官/commanders/<Commander>/`：确定官方等级、精通、威望、默认升级、默认能力命令。
- `references/sc2-build-96883-casc-export/`：追 Catalog、UserData、本地化、触发器和效果闭包。
- `原始mod/`：当前实现/回归目标，承载拿原 mod 续上的新项目；可作为实际接入状态依据，但不能反推官方设计基准。
- `合作指挥官版起义狂潮/`：半成品旧测试线索，不能反推设计结论，也不要直接混入当前实现线。

## 分层架构

推荐分成五层：

```text
官方数据提取层
  -> Profile 声明层
  -> Catalog 生成/补丁层
  -> XMFinal 运行时分发层
  -> 测试台与日志验证层
```

核心原则：

- 地图只传 `player`、`scenarioKind`、`commander`。
- 地图不判断某个 commander 的精通、威望、兵种升级。
- 科技建筑只承载研究按钮和能力，不决定某个兵种吃不吃威望补偿。
- `XMFinal.SC2Mod` 是统一 runtime owner。
- 指挥官差异由 profile 声明，少数不能静态表达的行为才进 runtime hook。

## 强度融合层

强度融合执行顺序：

```text
BaseCommander
  -> FullLevel15
  -> AllSixMasteries
  -> PrestigePositiveEffects
  -> NegativeSkipCompensation
  -> RuntimeHooks
  -> VerificationLog
```

建议 profile：

| Profile | 职责 |
|---|---|
| `CommanderPowerFusionProfile` | 声明等级满级、精通全满、威望正面融合的执行策略 |
| `CommanderLevelUnlockProfile` | 声明 15 级解锁项，以及满级后 roster 的新增、替换、变体 |
| `CommanderMasteryProfile` | 声明 6 项精通默认 30 点，并标记是否需要 runtime hook |
| `CommanderPrestigeEffectProfile` | 把官方威望拆成正面效果、负面代价、禁用项、补偿项、待审计项 |
| `CommanderRosterProfile` | 声明初始、满级、强度融合最终状态下要验证的单位、建筑、英雄、面板 |

## 威望处理规则

不要直接启用官方 `PlayerPrestige`。官方威望经常同时包含收益和代价，例如禁用单位、禁用能力、压制升级、提高费用、提高冷却、降低上限。

每个威望都要拆成：

```text
positive_catalog
positive_requirement
positive_runtime
positive_button
negative_disable_unit
negative_disable_abil
negative_suppress_upgrade
negative_cost
negative_cooldown
negative_cap
negative_stat
unknown_needs_casc
```

每个效果都要标记：

```text
keep
skip
conditional
needs_user_decision
needs_casc_audit
```

## 满级 roster 变化

这是后续实现和测试必须注意的点：满级后不是只多几个按钮，兵种清单本身也可能变化。

可能变化包括：

- 满级后新增可训练或可生成单位。
- 低级单位被高级变体替代。
- 训练入口指向不同单位。
- 终极进化加入最终清单。
- 英雄形态改变攻击方式、武器、行为和可用能力。
- 威望正面收益让某些单位或形态进入最终测试清单。

因此 `CommanderRosterProfile` 至少要区分三阶段：

| Stage | 含义 |
|---|---|
| `initial` | 官方基础状态审计清单，只用于对照和排错，不作为默认玩法状态 |
| `level15` | 当前默认 commander 状态：15 级全解锁后的单位、建筑和英雄状态 |
| `power_fusion` | 15 级 + 精通全满 + 威望正面融合后的最终测试清单 |

测试台里的 `full_units` 默认应等价于 `fusion_final_units`。排查官方基础链路时再显式跑 `initial_units`，但不能把它当作当前指挥官的默认实战状态。

## XMFinal 运行时入口

建议新增或收敛到这些入口：

```galaxy
XM_ApplyCommanderPowerFusion(player, commander)
XM_ApplyCommanderFullLevel(player, commander)
XM_ApplyCommanderAllMasteries(player, commander)
XM_ApplyCommanderPrestigeEffects(player, commander)
XM_RunCommanderPowerFusionHook(player, commander, hookKind)
XM_VerifyCommanderPowerFusion(player, commander)
```

调用位置：

```text
ReadCommander
  -> InitBaseCommander
  -> InitCommanderPanel
  -> ApplyCommanderPowerFusion
  -> VerifyCommanderRuntime
  -> StartScenario
```

runtime hook 只处理无法静态声明的行为，例如：

- 诺娃首个生产建筑、形态切换、超级隐形。
- 德哈卡克隆、首领、精华同步。
- 泰凯斯独狼视野检测。
- 泽拉图神器碎片上限和暗影顺劈龙卷风。
- 雷诺空军人口影响顶部面板充能。

## 测试台方案

测试台目标不是替代真实战役地图，而是降低基础闭包排错成本。它应当一次启动游戏后，能切换指挥官并验证初始化、强度融合、全 roster、面板、英雄形态、演化链和核心日志。

测试按钮建议：

```text
应用强度融合
验证等级
验证精通
验证威望
生成初始 roster
生成满级 roster
生成融合最终 roster
验证满级兵种变化
验证面板技能
验证英雄形态
验证演化链
Run All Smoke
```

单个指挥官流程：

```text
SetCommander
  -> ClearTestState
  -> InitBase
  -> InitPanel
  -> ApplyPowerFusion
  -> SpawnFusionFinalRoster
  -> VerifyRosterMutations
  -> RunPrestigeSmoke
  -> RunTechSmoke
  -> WriteSummary
```

测试结论要分清：

| 结论 | 测试台可判断 | 仍需新局或真实地图确认 |
|---|---|---|
| Catalog 对象存在 | 是 | 否 |
| profile 能读取 | 是 | 否 |
| 单位能创建 | 是 | 部分 |
| 满级 roster 是否包含最终兵种 | 是 | 具体战斗数值仍需确认 |
| 精通升级能加到 30 | 是 | 真实数值仍需确认 |
| 威望负面是否被跳过 | 部分 | 是 |
| 面板冷却、费用、触发器 | 部分 | 是 |
| 剧情任务语义 | 否 | 是 |

## 雷诺试点口径

雷诺当前作为第一个试点：

- 等级：15 级全解锁。
- 精通：6 项全部 30 点。
- 威望：只拆正面收益，不直接启用官方 `PlayerPrestige`。

已确认取舍：

- P1 保留生化部队生命值收益，不保留禁用矿骡。
- P2 保留推进器攻速、冷却减少、生命消耗，并关闭 1 级机械气耗减免；不保留移速负面。
- P3 保留星港前置放宽、星港单位气耗降低、空军人口加速顶部面板充能；不保留军械库/轨道基地前置放宽、星港建筑免气、作战单位晶体矿费用增加。

## 实施顺序

建议按闭环推进：

1. 闭环 0：Raynor、Nova、Abathur 的强度融合 profile。
2. 闭环 1：测试台 + `CommanderRosterProfile`，覆盖 `initial_units`、`level15_units`、`fusion_final_units`。
3. 闭环 2：科技链，先做 1 个指挥官、1 个兵种、1 个攻防组、1 个专属科技。
4. 闭环 3：英雄形态、演化和能力，例如诺娃形态、阿巴瑟终极进化、德哈卡吞噬/等级。
5. 闭环 4：扩展到全部指挥官，补日志解析和实机验证记录。

## 当前剩余风险

- 这是架构总结，还不是代码实现。
- profile、dispatcher、测试台按钮、日志解析脚本仍需落地。
- 部分精通和威望效果必须追 CASC 闭包，不能只看 tooltip。
- 同局切换 commander 时，升级、Bank、触发器、Dialog 控件可能残留；测试台结果只能证明基础闭包，不能替代真实地图新局验证。
