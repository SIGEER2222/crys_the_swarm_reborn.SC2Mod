# 架构回看：精通威望与兵种整理后的修订

日期：2026-05-27

## 结论

前面的控制反转方案方向是对的，但在整理完整指挥官精通、威望和兵种闭包后，需要补一个明确的“强度融合层”。否则等级、精通、威望、兵种科技、英雄技能和面板修正会继续混到地图初始化、科技建筑或零散触发器里。

修订后的架构应分成五层：

```text
官方数据提取层
  -> Profile 声明层
  -> Catalog 生成/补丁层
  -> XMFinal 运行时分发层
  -> 测试台与日志验证层
```

其中 Profile 声明层必须新增三类核心 profile：

```text
CommanderPowerFusionProfile
CommanderPrestigeEffectProfile
CommanderRosterProfile
```

## 为什么要新增强度融合层

整理雷诺和其它 17 个指挥官后，可以看到威望不是简单的“加一个 Upgrade”：

1. 很多 `PlayerPrestige` 同时包含正面和负面。
2. 负面经常是 `DisableUnit`、`DisableAbil`、`SuppressUpgrade`、费用提高、冷却提高、前置削弱。
3. 正面有些是纯 Catalog 字段，有些是 Requirement 桥接，有些是触发器/runtime 行为。
4. 精通全满会影响英雄、兵种、面板、研究费用、冷却和资源消耗。
5. 同一指挥官的多个威望可能修改同一个对象，例如泽拉图神器碎片、诺娃形态、沃拉尊时间停止。
6. 满级之后兵种清单本身也会变化，不只是多几个按钮；有些低级单位会被高级变体、终极进化、英雄形态或新可训练单位替代。

所以不能把“威望融合”塞进：

- 地图初始化。
- 科技建筑研究逻辑。
- 英雄技能接入。
- 面板技能初始化。
- 玩家 Bank 加点读取。

它应该是一个在 commander 初始化后统一执行的独立阶段：

```text
BaseCommander
  -> FullLevel15
  -> AllSixMasteries
  -> PrestigePositiveEffects
  -> NegativeSkipCompensation
  -> RuntimeHooks
  -> VerificationLog
```

## 新增 Profile 设计

### CommanderPowerFusionProfile

用于声明一个指挥官采用哪种强度融合规则。

```text
Id
Commander
Enabled
LevelMode
MasteryMode
PrestigeMode
ApplyOrder
LevelUnlockSet
MasterySet
PrestigeEffectSet
RuntimeHookSet
VerifySet
DebugTag
```

推荐值：

```text
LevelMode = FullLevel15
MasteryMode = AllSixMax
PrestigeMode = SelectedPositive
ApplyOrder = BaseCommander -> LevelUnlocks -> Masteries -> PrestigeEffects -> RuntimeHooks -> Verify
```

注意：这个 profile 不保存具体效果字段，只保存“采用哪套规则”。具体正负效果归 `CommanderPrestigeEffectProfile`。

### CommanderPrestigeEffectProfile

用于把每个官方威望拆成可保留和不可保留的独立项。

```text
Id
Commander
SourcePrestige
SourceUpgrade
EffectKind
CatalogObject
CatalogField
Operation
Value
KeepMode
RequiresRuntimeHook
RequiresRequirementBridge
RequiresButtonBridge
RequiresCompensationUpgrade
SkipReason
AuditStatus
TestCase
```

`EffectKind` 建议枚举：

```text
positive_catalog
positive_requirement
positive_runtime
positive_button
negative_disable_unit
negative_disable_abil
negative_suppress_upgrade
negative_cost
negative_cooldown
negative_cap
negative_stat
unknown_needs_casc
```

`KeepMode` 建议枚举：

```text
keep
skip
conditional
needs_user_decision
needs_casc_audit
```

示例：

```text
Raynor P3:
  keep positive_requirement: starport prerequisite relaxation
  keep positive_catalog: starport unit vespene reduction
  keep positive_runtime: air supply accelerates top-panel skills
  skip negative_requirement: armory/orbital prerequisite relaxation
  skip negative_catalog: starport building free gas
  skip negative_cost: combat unit mineral increase
```

### CommanderMasteryProfile

当前 `progression.json` 已能列出 6 项精通，但架构层仍需要一个可执行 profile，避免运行时读玩家 Bank。

```text
Id
Commander
MasteryUpgrade
Category
DefaultFusionLevel
ExpectedEffect
EffectOwner
AuditStatus
TestCase
```

强度融合默认：

```text
DefaultFusionLevel = 30
```

风险点：

- 研究费用、生产费用、面板冷却这类精通可能不是单纯加升级等级就生效。
- 需要用 `AuditStatus` 标记 `catalog-only`、`runtime-hook`、`needs-test`。

### CommanderLevelUnlockProfile

15 级全解锁不能再用旧的 8 槽 `CommanderAch.Upg` 表达。

```text
Id
Commander
Level
UnlockKind
Upgrade
Ability
AbilityCommand
ResearchButton
Requirement
RuntimeHook
RosterMutation
ReplacementUnit
FinalUnit
AuditStatus
```

`UnlockKind` 建议枚举：

```text
upgrade
ability_command
research_button
unit_unlock
unit_replace
unit_variant
hero_unlock
panel_unlock
runtime_hook
```

满级解锁必须记录对 roster 的影响：

- `unit_unlock`：满级后新增可训练/可生成单位。
- `unit_replace`：满级后训练入口或测试清单应从旧单位切到新单位。
- `unit_variant`：同一兵种出现等级后变体、强化版、英雄版或精英版。
- `runtime_hook`：例如德哈卡等级、阿巴瑟终极进化、诺娃形态这类不能只靠静态升级表达的变化。

这部分不能只写成“等级 15 已解锁”。后续生成测试台 roster 时，要能从 `CommanderLevelUnlockProfile` 推导出满级最终单位清单。

### CommanderRosterProfile

测试台和全单位展示不能靠地图手写 commander if/else，需要数据源声明“这个指挥官有哪些对象需要验证”。

```text
Id
Commander
RosterKind
RosterStage
ObjectKind
ObjectId
Count
SpawnZone
CreateMode
RequiredUnlock
RequiredPrestigeEffect
VariantOf
SupersedesObject
FinalObjectId
ExpectedAbilities
ExpectedWeapons
ExpectedBehaviors
ExpectedUpgrades
AuditStatus
```

`RosterKind`：

```text
full_buildings
full_units
initial_units
level15_units
fusion_final_units
hero_modes
panel_smoke
tech_smoke
evolution_smoke
prestige_smoke
```

这个 profile 的目标不是平衡，而是让测试台一次性创建并验证对象闭包。

`RosterStage` 用于区分：

| Stage | 含义 |
|---|---|
| `initial` | 1 级或基础 commander 状态下可见/可生成的单位 |
| `level15` | 15 级全解锁后的单位、建筑和英雄状态 |
| `power_fusion` | 15 级 + 精通全满 + 威望正面融合后的最终测试清单 |

测试台的 `full_units` 默认应该指向 `power_fusion`，而不是基础 1 级 roster。需要追溯基础链路时，再显式跑 `initial_units`。

## 运行时分发修订

`XMFinal.SC2Mod` 需要新增一个强度融合 dispatcher：

```galaxy
XM_ApplyCommanderPowerFusion(player, commander)
XM_ApplyCommanderFullLevel(player, commander)
XM_ApplyCommanderAllMasteries(player, commander)
XM_ApplyCommanderPrestigeEffects(player, commander)
XM_RunCommanderPowerFusionHook(player, commander, hookKind)
XM_VerifyCommanderPowerFusion(player, commander)
```

调用位置应在基础 commander 初始化之后、测试或地图玩法开始之前：

```text
ReadCommander
  -> InitBaseCommander
  -> InitCommanderPanel
  -> ApplyCommanderPowerFusion
  -> VerifyCommanderRuntime
  -> StartScenario
```

不要让地图自己调用某个指挥官的精通或威望函数。地图最多只传：

```text
player
scenarioKind
commander
```

## 和现有 Profile 的关系

新增 profile 不替代原来的初始化、科技和能力 profile，而是把它们串起来。

| 关注点 | Profile Owner |
|---|---|
| 开局基地、工人、运输、奖励 | `CommanderRuntimeProfile`、`CommanderScenarioLoadout` |
| 初始/满级/融合后的全单位与全建筑测试清单 | `CommanderRosterProfile` |
| 15 级解锁与满级后 roster 变化 | `CommanderLevelUnlockProfile` |
| 6 项精通全满 | `CommanderMasteryProfile` |
| 威望正负拆分 | `CommanderPrestigeEffectProfile` |
| 攻防和专属科技 | `CommanderUnitTechProfile` |
| 单位技能、按钮、需求 | `CommanderUnitAbilityProfile` |
| 单位属性归属 | `CommanderUnitStatProfile` |
| 演化、变体和形态 | `CommanderUnitEvolutionProfile`、`CommanderHeroModeProfile` |
| 顶部面板 | `CommanderPanelProfile` |

应用阶段：

```text

[XM_DBG][INFO][POWER_FUSION_LEVEL] commander=Nova level=15 unlocks=42 result=ok

[XM_DBG][INFO][POWER_FUSION_PRESTIGE] commander=Nova source=CommanderPrestigeNovaSuperCloak keep=superCloak,nukeRadius skip=disableKitSwap,disableResearch result=ok
```

## 测试台修订

之前的测试台设计正确，但现在要把“强度融合”作为独立测试项，而不是只测试初始化。

测试台按钮应增加：

```text
应用强度融合
验证等级
验证精通
验证威望
生成初始 roster
生成满级 roster
生成融合最终 roster
验证面板技能
验证英雄形态
验证演化链
验证满级兵种变化
```

单个指挥官测试流程：

```text
SetCommander
  -> ClearTestState
  -> InitBase
  -> InitPanel
  -> ApplyPowerFusion
  -> SpawnFusionFinalRoster
  -> RunPrestigeSmoke
  -> RunTechSmoke
  -> WriteSummary
```

全量冒烟测试：

```text
for commander in commanders:
  SetCommander
  ApplyPowerFusion
  VerifyLevel15
  VerifyAllMasteries
  VerifyPrestigeEffects
  SpawnFusionFinalRoster
  VerifyRosterMutations
  Summarize
```

注意：同局切换 commander 时，升级状态不一定可回滚。因此测试台结论分两类：

| 结论 | 可由同局测试台判断 | 需要新局确认 |
|---|---|---|
| Catalog 对象存在 | 是 | 否 |
| profile 能读取 | 是 | 否 |
| 单位能创建 | 是 | 部分 |
| 满级 roster 是否包含最终兵种 | 是 | 具体战斗数值仍需确认 |
| 精通升级能加到 30 | 是 | 真实数值仍需确认 |
| 威望负面是否被跳过 | 部分 | 是 |
| 面板冷却、费用、触发器 | 部分 | 是 |

## 架构边界修订

### 地图层

地图只负责剧情和场景语义。

允许：

```text
XM_CreateCommanderScenarioSquad(player, scenarioKind)
XM_RunScenarioObjective(...)
```

不允许：

```text
if commander == Nova then disableKitSwap = false
if commander == Raynor then add MasteryRaynorHyperionCooldown
if commander == Zeratul then artifactMax = 999
```

### 科技建筑层

科技建筑只负责承载研究按钮和研究能力。

不允许让科技建筑决定：

- 哪个威望跳过费用负面。
- 哪个精通加多少点。
- 哪个单位吃哪个官方威望补偿。

### 指挥官 hook 层

hook 只处理无法静态声明的运行时行为：

- 诺娃首个生产建筑/形态切换。
- 德哈卡克隆、首领、精华同步。
- 泰凯斯独狼视野检测。
- 泽拉图神器碎片无上限与暗影顺劈龙卷风叠加。
- 雷诺空军人口影响顶部面板充能。

hook 必须有 profile 入口和日志，不能只靠裸 if/else。

## 实施顺序修订

原方案的“闭环 A/B/C”仍保留，但前面要插入一个新的闭环。

### 闭环 0：强度融合 profile

范围：

- Raynor、Nova、Abathur 三个指挥官。
- 15 级全解锁。
- 6 项精通全满。
- 威望只取已确认正面收益。

交付：

- `CommanderPowerFusionProfile`
- `CommanderMasteryProfile`
- `CommanderLevelUnlockProfile`
- `CommanderPrestigeEffectProfile`
- `CommanderRosterProfile` 支持 `initial`、`level15`、`power_fusion` 三阶段
- `[XM_DBG][POWER_FUSION_*]` 日志
- 测试台按钮：应用融合、验证等级、验证精通、验证威望、验证满级兵种变化

### 闭环 1：测试台 + roster

范围：

- Raynor、Nova、Abathur。
- `standard_base`
- `full_units`
- `level15_units`
- `fusion_final_units`
- `panel_smoke`
- `prestige_smoke`

交付：

- `CommanderRosterProfile`
- `XMTestBench_RunRoster`
- `XMTestBench_VerifyRosterMutations`
- `XMTestBench_RunPrestigeSmoke`
- 缺对象/缺能力/缺威望效果日志

### 闭环 2：科技链

范围：

- 1 个指挥官。
- 1 个兵种。
- 1 个攻防升级组。
- 1 个专属科技。

沿用原方案。

### 闭环 3：英雄形态、演化和能力

范围：

- 诺娃形态切换。
- 阿巴瑟终极进化。
- 德哈卡吞噬/等级。

沿用原方案，但必须接入强度融合验证。
