# Codex 自治执行规则

这份文档给人看。目的不是教怎么写代码，而是让以后下任务时，Codex 更接近“连续推进、少打断、自己收口”的工作方式。

对应机器规则见仓库根目录：

- `AGENTS.md`

## 适用场景

当你希望 Codex 连续干活，而不是做一步停一步时，用这套规则。

典型场景：

- 指挥官移植收口
- 地图分支补齐
- 文档整理
- 静态验证 + live 验证
- 长链路排查

## 最推荐的下达方式

不要只说：

- `看下这里`
- `然后呢`
- `你先分析`

更有效的说法是：

```text
从现在开始按自治模式执行。

目标：
- 把 <任务目标> 做完，不要只分析。

执行要求：
- 先自己读代码和文档。
- 缺信息时按当前仓库做保守假设。
- 不要每一步都停下来问我。
- 可以自己补脚本、补文档、补验证。
- 每完成一段就继续下一段。

停止条件：
- <验证1> 通过
- <验证2> 通过
- <文档> 已更新

只有这些情况才允许来问我：
- 会做破坏性操作
- 会覆盖不明确的现有改动
- 必须人工交互
- 真的卡死
```

## 这套规则的核心

### 1. 默认闭环，不默认汇报

除非你明确说“只要分析”或“先别改”，否则 Codex 应默认：

- 直接改
- 自己验证
- 自己修下一轮
- 最后一次性汇报

### 2. 没有工具，不等于不能做

如果没有现成脚本、自动化或 helper，Codex 仍应优先：

- 用仓内已有脚本
- 手动读代码链路
- 补最小必要文档
- 先完成任务，再考虑把流程工具化

也就是说：

- 工具是加速器
- 不是开始工作的前提

### 3. 长任务要主动留下“可续跑痕迹”

理想状态下，哪怕会话中断，下一轮也不该重新摸半天。

因此长任务默认应留下：

- 当前状态文档
- 归档说明
- 验证脚本
- 阶段结果摘要

## 对这个仓库尤其重要的几条

### 指挥官项目

- 优先以 `XMFinal.SC2Mod` 为统一 runtime owner
- 地图只做 mission-specific 分支
- Launcher 只是入口，不是完成标准
- live 验证比字符串命中更重要

### 文档项目

- 阶段稿、handoff、规划稿不要混在主入口
- 当前有效文档应尽量少
- 历史文档应归档，而不是删除

## 什么时候仍然应该打断

即使是自治模式，也不是任何事都硬做。

应打断的情况只有少数几类：

1. 要删、覆盖或回退不明确归属的现有改动
2. 需要外部账号、人工点击、额外权限
3. 任务目标本身互相冲突
4. 继续做只会制造更大不确定性

## 你可以期待的结果

如果按这套规则下任务，理想输出不应是：

- 一堆计划
- 一堆问题
- 一半代码
- 一句“下一步建议”

而应更接近：

- 代码已改
- 文档已同步
- 验证已跑
- 剩余风险已明确

## 和“跑一整夜”的关系

真正影响连续推进的，通常不是模型能不能继续思考，而是：

1. 任务目标太松
2. 停止条件没写清
3. Codex 不确定哪些事可以自己决定
4. 关键信息只在聊天里，没有落到仓库

这份规则的作用，就是把第 3 和第 4 点尽量固化到仓库里。
