## 当前结论

本轮对比口径已经切到新的官方原始文本镜像，旧 `references/*` 不再作为事实源。18 个指挥官的 wiki 中文主名单均已匹配到官方 JSON、补充 ID 或当前/底层 Catalog，没有剩余“中文名完全对不上”的项。

当前最重要的区别是：主名单命中不等于 active 按钮链路闭合；单个指挥官模块缺 CUnit 也不等于运行时缺 CUnit。脚本现在会先按 `XMFinal.SC2Mod/DocumentInfo` 递归建立运行闭包，再判断按钮产物是否真的缺失。

## 总体优先级

1. 先修当前模块、XM共享、XMFinal运行闭包、底层基础镜像都没有的露出产物：按钮会直接训练、建造或变形到不存在的 CUnit。
2. 再查“外来生产链露出”：产物能解析，但生产者不属于该指挥官官方体系，常见于 Nexus/Probe/SISCV 这类跨指挥官命令卡。
3. 再处理只在官方合作镜像命中的项：这类通常是待迁移 Catalog、TopBar 召唤或官方 JSON 混入。
4. 再确认底层基础镜像命中项：这类不一定错，但必须靠地图/Mod 依赖和实机按钮确认。
5. 官方 JSON 有但 wiki 主名单未列的英雄、工人、基础建筑默认不按缺失修，除非当前按钮链路或开局实机证明缺。

## 下一步建议

1. 先看“命令卡露出产物缺 CUnit”：这是最接近实机按钮风险的静态入口。
2. 建筑专项优先查露出命令里 `Build*` 的项；隐藏 `Build*` 只保留在降级线索，不要盲目补建筑。
3. `InfoArray` 有但命令卡未露出的典型例子包括斯旺/诺娃的富矿精炼厂、轰炸平台残留，以及霍纳与汉的旧炮塔/科学设施残留。
4. 斯托科夫 `SIBarracksUpgradeToLevel2` 此前命中来自 XML 注释，当前脚本已剔除注释后再扫描。
5. 官方镜像只说明“官方曾有该 Catalog”，不代表 active 线会读取；当前 active 线先以 `XMFinal.SC2Mod/DocumentInfo` 运行闭包为准。

## XML 排查路线

每个指挥官按这个顺序查，不要只看静态 `CUnit`：

1. `UnitData.xml` 是否有目标 `CUnit`。
2. 生产者 `CUnit` 是否存在，且是否挂了对应 `AbilArray`。
3. 命令卡 `CardLayouts` 是否露出对应 `AbilCmd`。
4. `AbilData.xml` 的 `InfoArray` 产物是否指向存在的 `CUnit`。
5. 官方镜像只作为事实参考；最终修复落到 `合作指挥官版起义狂潮/Mods/XM/<Commander>.SC2Mod`。
