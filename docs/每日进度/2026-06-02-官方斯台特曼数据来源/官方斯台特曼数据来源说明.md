# 官方斯台特曼数据来源说明

生成时间：2026-06-02

## 结论

官方合作指挥官斯台特曼确实定义了单位、建筑、按钮/命令卡、效果和生产链路。

前一次判断中把 `starcoop.sc2mod` 的总入口当成了主要事实源，这是不准确的。`commanderdata.xml` 只提供 `Stetmann -> PlayerCommanders;ZergStetmann` 的入口映射；真正的斯台特曼单位、建筑、技能、按钮、效果，大量定义在官方专属 commander 模块 `egonstetmann.sc2mod` 里。

因此，正确说法应是：

- 可以通过官方斯台特曼数据反推官方原版斯台特曼的兵种、建筑、技能机制和生产链。
- 不能只看 `commanderdata.xml` 就下结论。
- 不能把官方对象直接等同当前 Mod 对象；当前 Mod 仍需要和 `XMStetmann.SC2Mod` 做逐项映射确认。

## 需要谨慎标注的点

`ViperStetmann` 在官方和当前 Mod 的 `LarvaTrainStetmann` 中都被引用：

- 官方 `abildata.xml`：`Train8 -> ViperStetmann`
- 当前 Mod `AbilData.xml`：`Train8 -> ViperStetmann`

但在本次快速核对中，未在官方 `egonstetmann.sc2mod/base.sc2data/gamedata/unitdata.xml` 或当前 `XMStetmann.SC2Mod/Base.SC2Data/GameData/UnitData.xml` 中找到独立的：

```xml
<CUnit id="ViperStetmann">
```

因此 `ViperStetmann` 后续要单独追：

- 是否继承自其他依赖模块。
- 是否只保留按钮/Actor 引用。
- 是否是当前 Mod 中的缺口。
- 是否官方也通过其他 Catalog 层补齐。

## 推荐后续追踪方式

以后追斯台特曼，不要只从 `commanderdata.xml` 开始判断。推荐顺序：

1. 先读结构化官方资料：

```text
游戏数据/官方合作指挥官/commanders/Stetmann/
```

2. 再追官方原始 Catalog：

```text
游戏数据/官方SC2原始文本镜像/mods/starcoop/commanders/egonstetmann.sc2mod/base.sc2data/gamedata/
```

3. 最后映射当前 Mod：

```text
合作指挥官版起义狂潮/Mods/XM/XMStetmann.SC2Mod/
```

4. 对每个对象标记状态：

- 官方定义存在，当前同名存在。
- 官方定义存在，当前改名或拆分。
- 官方引用存在，但当前/官方未找到本地 `CUnit`，需要追依赖。
- 当前存在但官方无同名，可能是 Mod 自定义。

## 修正后的口径

官方斯台特曼确实可以反推出官方兵种、建筑、按钮、效果和生产链。

不准确的是说“不能通过官方斯台特曼反推”。准确说法是：

> 不能只通过 `starcoop.sc2mod/base.sc2data/gamedata/commanderdata.xml` 这个总入口反推；必须展开官方 `egonstetmann.sc2mod` 和结构化的 `commanders/Stetmann` 数据。展开后，官方斯台特曼的核心链路是明确存在的。当前 Mod 是否完整继承或改写这些链路，则需要和 `XMStetmann.SC2Mod` 做逐项映射。
