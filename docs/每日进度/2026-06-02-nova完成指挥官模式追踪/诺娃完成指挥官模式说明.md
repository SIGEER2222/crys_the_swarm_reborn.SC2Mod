# 诺娃完成指挥官模式说明

本文用当前 Mod 中已经相对闭环的诺娃作为样例，说明一个指挥官的名册、建筑、兵种、顶部面板、Ability、Effect、产出单位之间是如何串起来的。

## 结论

诺娃的模式不是把所有东西都放在 `XMFinal.SC2Mod`。更准确的边界是：

| 层级 | Nova 当前模式 | 主要职责 |
| --- | --- | --- |
| `XMFinal.SC2Mod` | 运行名册、别名入口、测试台/统一框架 helper | 告诉统一框架“Nova 使用哪个运行模块、有哪些单位/建筑、官方 ID 映射到哪个运行 ID” |
| `XMNova.SC2Mod` | 实际 Catalog 定义 | 定义 Nova 私有单位、建筑、训练/研究技能、效果、行为、按钮、模型、触发器 |
| `XMCore.SC2Mod` | 少量共享顶部面板机制 | 例如 `SOAStickyLine` 这种可被多个指挥官复用的公共面板 helper |

所以，`XMFinal` 可以引用各个指挥官模块里的 `UnitData.xml` 定义；Nova 证明了“运行索引在 XMFinal，Catalog 实体在指挥官模块”是可行模式。当前 `XMFinal` 承载过多私有 catalog 的问题，应该按这个边界逐步收敛。

## 2. 建筑如何串到生产单位

建筑链路的读法是：

```text
CUnit 建筑
-> AbilArray 挂载训练/研究/建造能力
-> CardLayouts.LayoutButtons 暴露按钮和 AbilCmd
-> CAbilTrain / CAbilWarpTrain / CAbilBuild / CAbilResearch 的 InfoArray
-> Unit 或 Upgrade
-> 如果 Unit 是 spawner，再经 Behavior.InitialEffect -> EffectSet -> CreateUnit 生成最终单位
```

## 3. Nova 的 spawner 生产模式

Nova 的兵营/重工/星港不是直接训练最终战斗单位，而是训练 `*_BlackOpsSpawnerUnit`。这些 spawner unit 出生后挂一个 `CBehaviorBuff`，该 Behavior 的 `InitialEffect` 再创建最终战斗单位并移除 spawner。

典型完整链路：

```text
BarracksNova 面板按钮 TrainMarineNova
-> AbilCmd BarracksTrainNova,Train1
-> CAbilWarpTrain/BarracksTrainNova InfoArray[Train1]
-> Unit=Marine_BlackOpsSpawnerUnit
-> Marine_BlackOpsSpawnerUnit.BehaviorArray=MarineBlackOpsSpawner
-> MarineBlackOpsSpawner.InitialEffect=MarineBlackOpsSpawnerSet
-> MarineBlackOpsSpawnerSet
-> MarineBlackOpsSpawnerCreateUnit + KillRemove
-> SpawnUnit=Marine_BlackOps, SpawnCount=4
```

对应表：

| 生产建筑 | Ability/Cmd | 直接训练单位 | Behavior | EffectSet / CreateUnit | 最终产出 |
| --- | --- | --- | --- | --- | --- |
| `BarracksNova` | `BarracksTrainNova,Train1` | `Marine_BlackOpsSpawnerUnit` | `MarineBlackOpsSpawner` | `MarineBlackOpsSpawnerSet` -> `MarineBlackOpsSpawnerCreateUnit` | `Marine_BlackOps` x4 |
| `BarracksNova` | `BarracksTrainNova,Train2` | `Marauder_BlackOpsSpawnerUnit` | `MarauderBlackOpsSpawner` | `MarauderBlackOpsSpawnerSet` -> `MarauderBlackOpsSpawnerCreateUnit` | `Marauder_BlackOps` x2 |

| `FactoryNova` | `FactoryTrainNova,Train1` | `Goliath_BlackOpsSpawnerUnit` | `GoliathBlackOpsSpawner` | `GoliathBlackOpsSpawnerSet` -> `GoliathBlackOpsSpawnerCreateUnit` | `Goliath_BlackOps` x2 |

## 4. 兵种技能和被动如何串

战斗单位本体也遵循同一套读法：

```text
CUnit 单位
-> AbilArray 挂载主动技能
-> BehaviorArray / WeaponArray 挂载被动、武器、常驻效果
-> CardLayouts.LayoutButtons 暴露主动技能或被动图标
-> Ability 的 Effect / Upgrade / Requirement 决定技能效果和解锁条件
```

示例：

| 单位 | 定义位置 | 技能/被动连接 |
| --- | --- | --- |
| `Marine_BlackOps` | `XMNova.../UnitData.xml:924` | `AbilArray Link="NovaSuperStim"`，按钮 `NovaSuperStim,Execute`；被动按钮 `CombatShield`、`LaserTargetingSystemMarine` 通过 Requirements 显示 |
| `Banshee_BlackOps` | `XMNova.../UnitData.xml:1631` | `AbilArray Link="Banshee_BlackOpsAirstrike"`，按钮 `Banshee_BlackOpsAirstrike,Execute`；Ability 在 `AbilData.xml:1152`，EffectSet 在 `EffectData.xml:1663` |
| `Raven_BlackOps` | `XMNova.../UnitData.xml:1706` | 挂 `SeekerMissileNova`、`BuildAutoTurret_BlackOps`、`PlaceHealingDrone`，按钮可继续追到创建 `HealingDrone` / `NovaACLaserTurret` 的 effect |
| `Liberator_BlackOps` | `XMNova.../UnitData.xml:1411` | 诊断显示它的单位技能会创建 `LiberatorAGUnitNova`，对应运行变形/目标模式链 |

这里的升级和需求主要从 `CAbilResearch.InfoArray.Upgrade`、`UpgradeData.xml`、`RequirementData.xml` 继续往下追。一个单位是否“技能齐”，不能只看 `AbilArray`，还要看按钮是否出现在 `CardLayouts`，以及对应 `Requirements` 是否是本指挥官自己的条件。

## 6. 哪些东西应该留在 XMFinal，哪些应该回指挥官模块

从 Nova 看，合理拆分可以按下面判断：

| 应保留在 `XMFinal` | 应放在指挥官模块 |
| --- | --- |
| `CommanderRuntimeRoster` 这种统一运行名册 | `CUnit` 的私有单位/建筑定义 |
| 指挥官官方 ID 到运行 ID 的 alias 关系 | `CAbilTrain`、`CAbilWarpTrain`、`CAbilResearch` |
| 统一测试台、统一创建 helper、跨指挥官公共 runtime | `CEffectCreateUnit`、`CEffectSet`、`CBehaviorBuff`、武器、Actor、Model |
| 真正共享的顶部面板 helper，例如 `SOAStickyLine` | 指挥官自己的面板 caster、按钮布局、成本、冷却、触发器 |
| 跨指挥官共享 requirement / button / text | 指挥官专属升级、需求、按钮、文本 |

当前 `XMFinal` 中仍能搜到不少 Nova 私有 Ability/Effect 的重复定义，这说明 `XMFinal.SC2Mod` 的确承担了过多历史包袱。后续补其他指挥官时建议以 Nova 的 `XMNova.SC2Mod` 为边界模板，而不是继续把指挥官私有 catalog 塞进 `XMFinal`。

## 7. 后续补齐其他指挥官的检查顺序

1. 先查 `XMFinal CommanderRuntimeRoster` 是否登记该指挥官的 `RuntimeModule`、单位、建筑。
2. 再查 `CommanderRosters.galaxy` / `CommanderBuildings.galaxy` 是否有官方 ID 到运行 ID 的 alias。
3. 进入指挥官模块的 `UnitData.xml`，找每个建筑的 `AbilArray` 和 `CardLayouts`。
4. 用 `CardLayouts.LayoutButtons.AbilCmd` 反查 `AbilData.xml`。
5. 对 `CAbilTrain/CAbilWarpTrain`，继续追 `InfoArray.Unit`；如果是 spawner unit，继续追 `BehaviorArray -> InitialEffect -> EffectSet -> CreateUnit -> SpawnUnit`。
6. 对 `CAbilResearch`，继续追 `InfoArray.Upgrade -> UpgradeData.xml -> AffectedUnitArray/EffectArray`。
7. 对战斗单位，查 `AbilArray`、`BehaviorArray`、`WeaponArray`、`CardLayouts`，确认主动技能、被动图标、需求都在本指挥官链路内。
8. 对顶部面板，优先找 `CoopCaster*` / `SoACaster*` 这类全局 caster 单位，再追其 `AbilArray`、`CardLayouts`、Ability、Effect、触发器。
9. 最后跑 `export-commander-tech-tree-diagnostics.mjs`，看未解析 Ability、Effect、非本指挥官产物、跨指挥官 requirement 是否异常。

## 8. 本次静态追踪的注意点

- 本次没有 SC2 runtime 环境，只做静态 catalog/脚本链路追踪。
- `NovaDefensiveMatrixDrone` 的 Ability 没有显式 `<Effect>` 字段，但存在同名 `CEffectCreateUnit`；这类同名隐式/继承链需要 runtime 或更深 catalog 规则确认。
- 诊断报告中的 `Barracks`、`CommandCenter`、`MissileTurret`、`AutoTurret` 是 runtime roster 的原始项；实际构建链路应优先看 Galaxy alias 出来的 `BarracksNova`、`CommandCenterNova`、`MissileTurretNova`、`AutoTurret_BlackOps`。
- spawner 模式会让“直接生产目标”和“最终战斗单位”不同；补其他指挥官时不要把 `*_SpawnerUnit` 误判成缺失或污染，必须继续追 behavior/effect。
