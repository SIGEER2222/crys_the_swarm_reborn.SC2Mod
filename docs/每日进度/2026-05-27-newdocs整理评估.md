## 结论

`docs/newdocs` 现在更接近一套“新的实施蓝图 + 施工底稿”，不是可以直接当官方闭包真值表的最终数据源。

它有两层价值：

1. 可以直接作为后续接入方向和模块拆分依据。
2. 不能直接把其中所有按钮、英雄、面板、运输机候选当成已经证实的官方最终闭包。

## 当前最有价值的部分

1. 架构主线已经收口：
   - `XMFinal.SC2Mod` 作为 runtime owner
   - 强度融合层独立出来
   - 指挥官 profile 化
   - 测试台单图回归

2. 文档结构清楚：
   - 总结
   - 架构修订
   - IoC 接入
   - 测试台
   - 模块拆分
   - 18 指挥官细化

3. 单指挥官文档已经把工作面拆到了可施工粒度：
   - 顶栏
   - 英雄
   - 普通单位
   - 基地
   - roster
   - 精通/威望
   - 科技
   - cargo
   - 特殊机制
   - 个性机制

## 当前不能直接当“真相”的地方

1. `command_cards.json` 候选污染仍然存在。
   - 文档自己也承认共享对象会串出别的指挥官按钮。
   - 例如雷诺文档里还能看到 `GhostAcademyNova`、`SwannBarracks` 这类跨指挥官按钮候选。

2. `heroes.json=0` 的文档不能等同于“该指挥官没有英雄”。
   - 阿巴瑟、雷诺、泽拉图等文档都明确写了还要继续追 CASC 或实机。
   - 这说明当前英雄层仍是不完整输入，不是最终结论。

3. “顶部技能栏”章节混入了不少并非顶部面板的命令。
   - 例如凯瑞甘、阿巴瑟、雷诺文档里都把研究或变异命令列进了这一章。
   - 这更像“默认能力命令全集候选”，不是已经筛好的面板技能表。

4. 运输机空投部分大多还是设计草案。
   - 它的价值在于接入规则和 profile 方向，不在于当前 loadout 数值已经可信。

## 实际可用口径

后续如果要继续实现，建议把 `docs/newdocs` 当成：

1. 架构和模块边界说明书。
2. 指挥官施工清单。
3. 测试台设计说明。

不要把它当成：

1. 官方数据最终真值库。
2. 已经过完 Requirement / Ability / Actor 闭包的成品表。
3. 可直接复制进 runtime 的最终 roster / panel / hero 清单。

## 下一步建议

如果继续沿这套资料推进，优先顺序应是：

1. 先用 `newdocs` 定模块和 runtime 接口。
2. 真正的数据闭包继续以 `游戏数据/官方合作指挥官/` + live game data 为准。
3. 先落 `阶段 0 静态校验` 和 `阶段 1 三指挥官测试台最小闭环`，不要先扩 18 指挥官细节实现。
